# .NET 服务诊断案例

以下为合成判断示例，不是目标服务的实测结果。操作仍受原任务授权约束。用示例校准证据与下一步，不能仅因描述相似就套用原因；通用方法见[.NET 诊断](dotnet.md)。

## 请求慢、CPU 低：两条不同路径

原场景为同一应用查询逐渐变慢。第一组观察中，Data 池 used 达到本池 max，Locks 池空闲，SQL 执行耗时仍短；原请求同时有连接取得等待。下一步查 Data 连接持有者、事务范围和释放。Locks 空闲不证明 Data 容量可用；这些观察也不能单独证明泄漏。

第二组观察中，池有空闲连接，但线程池线程持续增长、完成速率不足，原慢请求的等待栈出现同步等待异步结果。下一步对照该调用链及同窗跟踪，检查同步阻塞；不能沿第一组去扩连接池。线程池队列某次采到零不能覆盖其他证据。

恢复后分别比较同包、同请求与同数据量下的等待、完成量和错误，保留原失败组。低 CPU 或单次响应变快不能代替原场景恢复。

## RSS 保持高位：先区分保留对象与其他内存

原场景为读取若干轮后进程工作集增长。相同业务阶段的最近回收堆基线稳定，GC 提交内存和工作集仍高。下一步区分池保留、碎片、非托管分配、映射及容器内存；现有证据不足以判定托管泄漏。

若可比堆样本显示某类对象及保留字节持续增长，再追根路径中的缓存、订阅或未结束任务，并核对真实活跃实体与自然释放条件。不能用分配总量当存活量，也不能强制 GC 或重启后只报告下降值。

## 保存报错：业务提交和提交后动作分别回读

原场景为保存返回 500。原操作的记录已回读存在，关联日志显示提交后回调失败；同窗 `AiInfra.Abp.Uow` 也观察到 post-commit 失败。先保留原写入结果，沿原回调及已有恢复方式查后续动作，不能重新发送整笔写入。

如果只有聚合指标、没有原操作回读或请求关联，则结果仍未知。不能把另一个请求的 post-commit 失败归给本笔保存；继续按原业务标识查询，不从“500”推导“已回滚”。

## 诊断端点不可达：保留现场并说明缺口

原场景为容器中进程正常处理请求，但工具找不到诊断端点。先核对容器 PID、UID、临时目录/挂载、端点配置、运行时和工具架构。能用已有日志和监控时继续收集，说明未取得栈或跟踪的影响。

原请求仅授权诊断时，不为连接工具而重启服务、开放远程诊断口、放宽容器权限或采集全机。Windows 的成功样例也不证明 Linux 容器附加方式已验证。

## 使用案例检验改写

固定原始问题、当时可得记录及源码或包，不把上述判断答案放进执行输入。执行者需要实际读取对应工具输出、调用链或业务回读，保留支持、反证和未知项。未参与编写的案例应另行保留；作者走查、工具实测和独立模型执行分别报告。仅命中指标名、回答下一步或目录一致，不能证明实际排障能力已改善。
