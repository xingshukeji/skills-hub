# 性能优化方法

用于明确的延迟、吞吐、CPU、内存或 IO 优化目标，也供业务开发、客户端和审查按需使用。沿原任务的结果与授权执行；源码分析、隔离实验、真实服务取证分别选择，不因需要指标而启动服务、增加压测或部署。

## 从业务代价选择切入点

先固定原动作、有效完成量、数据形状、当前实现或制品和目标。规模同时看条数、行宽、字段类型、大值、关系数量、读写比例及数据倾斜。延迟按用户发起到可继续工作的完整区间计算；吞吐按实际成功业务量计算，保留错误、取消和慢样本。

沿调用与数据流标出重复计算、编码与复制、内存保留、外部往返、排队、锁和持久化。先用现有日志、计数、调用栈与查询证据形成假设，再决定是否采样。运行中 .NET 的指标与工具选择见[服务诊断](../services/references/dotnet.md)。

| 主要代价 | 需要区分的证据 | 可比较的优化方向 | 相关取舍 |
|---|---|---|---|
| 计算 | 单次 CPU 时间、热点、调用次数及算法随规模的增长 | 减少重复遍历或解析，选择合适算法和索引，再看编译、向量化及热点代码 | 预计算的失效条件、额外保留量及初始化成本 |
| 分配与 GC | 分配速率、回收暂停、回收后存活量、堆外内存及容器限制 | 减少中间表示与复制，缩短保留时间，流式处理，按实际所有权选择缓冲复用 | 池的保留和清理成本、借用期限、异常归还及并发共享 |
| 数据库与文件 IO | 往返次数、读取/写入字节、SQL 与锁等待、连接持有及缓冲 | 合并已允许的操作，批量、投影、顺序读取、流式写出，检查计划和索引 | 事务、顺序、原子性、重试及回执；异步写入何时真正完成 |
| 排队与同步 | 到达率、有效完成率、在途量、线程/锁/连接等待 | 去掉不必要的同步等待，缩短临界区，以现有资源控制在途工作 | 并发增加后的峰值内存、争用、取消排空和普通业务尾延迟 |
| 网络与多实例 | 每层调用、重试和传输量，跨进程等待及同一请求的实际关联 | 减少重复获取，合并往返，传播截止与取消，按原协议背压或幂等恢复 | 重试放大、热点、缓存一致性、租约、重复提交和部分成功 |
| 客户端 | 可见操作耗时、主线程工作、重复渲染、媒体和订阅保留 | 减少重复加载与更新，渐进显示、虚拟化，释放已退出页面持有资源 | 完整数据、滚动/选择、草稿、无障碍和迟到结果的归属 |

按证据选方向，不把整表变成每次任务的检查清单。先减少实际工作量和往返，再比较编码、布局和复制等局部成本；已经证明局部热点主导成本时，可以直接优化该热点。配置值从项目预算和业务约束取得，不推广某次实验的并发、文件条数或时限。

## 研究候选并放回项目

从目标入口核对语言、框架、运行时、依赖锁、硬件和实际消费版本。遇到新 API、实现机制或版本差异，查该版本官方说明、源码与有条件可复现的开源实践。记录它减少的具体工作、适用前提、维护代价及最小对照；不能从名称相似或新版介绍推导本项目已受益。

先查框架、驱动和项目现有机制。已有顺序读取、批处理、索引、缓冲池或执行名额时，比较其真实实现，不另造同名包装。只有实际缺口才引入新依赖、缓存、队列或协议；升级本身不是性能修复的默认步骤。

把候选落实为当前业务入口 → 实际热点或等待 → 拥有该事实的组件 → 调用方和数据 → 可观察结果。项目有源码时定位符号、类型与测试；公开包消费者按已交付 API 和包判断，不要求其取得平台私有源码。命令、环境和部署入口仍由目标 Runbook 持有。

.NET 后端需要实施时，可按目标可用的 AiInfra 技能读取[后端专项](https://github.com/xingshukeji/skills-hub/blob/main/skills/shzw-aiinfra-development/modes/performance/GUIDE.md)；客户端按其技术栈与[可见性能方法](https://github.com/xingshukeji/skills-hub/blob/main/skills/shzw-client-development/modes/application/references/performance.md)处理。只有命中对应技术时才展开，不要求加载全部技能。

目标是 Node.js 服务、宿主或 Runtime 时，读[Node.js 专项](references/node.md)，区分事件循环、V8/堆外内存、流与工作线程。

## 同时比较收益与工程代价

对保留的方案说明它减少什么、增加什么，以及谁能维护它。以正常路径能否顺着读懂为起点，核对状态所有者、调用顺序、数据依赖、失败与恢复。命名表达业务或资源含义；注释解释不明显的不变量和取舍。函数拆分围绕职责和生命周期，不追求固定行数，也不把关键约束藏进跨层回调或万能工具。

在收益相近时，优先现有标准机制、较少状态和较直接的数据流。自定义内存所有权、unsafe、复杂缓存失效、多级队列或并发状态机需要有与其维护风险相称的实测收益。修复局部热点时检查能否同时去掉重复分支；不要依靠更多开关和例外维持两套行为。

CPU、分配、保留内存、IO、吞吐和尾延迟分别报告。池化可能增加清理成本或保留量；缓存可能增加内存及失效责任；并发可能降低单任务时间而损害其他请求。达到原目标且代码更清楚的方案，可以优于某一项微基准最好但整体代价更高的方案。预算确需改变时说明业务影响，不通过截断数据、放宽授权、取消事务或换更大资源隐去代价。

## 证明原业务仍成立

先记录要保留的业务结果、协议、数据与失败行为，再改实现。对纯转换可用冻结参考、独立样例或性质比较检查旧新结果；有状态链路检查原入口、持久回读及相关消费者。功能与资源如何一起验证见[功能回归与性能验证](https://github.com/xingshukeji/skills-hub/blob/main/skills/shzw-testing/references/functional-regression.md)。

组件实验先证明候选减少了目标成本；最终结论回到代表性业务动作。保持影响判断的版本、数据、冷/热状态、资源、负载和计时边界可比。诊断开销、共享负载变化或结果不稳时，按实际疑点补同环境旧版本对照，不要求每次小改执行固定轮数或全仓散列。

保留没有收益或回退的实验。分配减少不等于峰值内存下降，吞吐提高不等于交互更快，局部更快不等于完整流程更快。采样和正式计时的差异明确标注，不把不同候选的最好分段拼成整体。公共库或打包边界发生变化时，再核对实际消费者使用的包和行为。

收口给出业务结果、资源变化、维护取舍和证据边界。只形成局部证据时保留整体未验证项；已达到目标时，不为追逐更小数字无依据扩大改动。

## 历史校准中的负载与门槛

这些决定用于选择正反例，数值不是其他项目的默认预算。

- 2026-10-26，Workforce 用户把“2000 人容量”明确为 2000 人在线、按实际操作频率使用（聊天 `01a17254-3a24-7950-92b3-9205665d28a0`）。在线身份数、同时在途请求数与每秒到达量分别测量；不能用 2000 个请求同时发出代替该验收，也不能用少量成功请求证明 2000 人已通过。
- 2026-10-25，用户否定没有需求依据的构建机 8 GiB 空间门槛，且不希望没有实际问题就清缓存（聊天 `01a16e4c-3fe3-7a90-9d27-c298209b452b`）；11 月 1 日又要求逐项评估所有门槛（聊天 `01a19492-9e76-7ab0-8aa4-3eeedc26587d`）。先识别真实失败、标准机制和业务等待成本，再决定删除、调整或保留。不能把“评估能否删除”改写为一律无限等待，也不删除取消、生命周期和数据完整性保护。
- 2026-10-29，用户要求先查共享平台无响应的原因，再决定恢复动作（聊天 `01a1855d-64a8-7423-b321-a9d926785c62`）。保留已有现场，区分客户端等待、代理不可达、平台进程和数据库资源；超时不能直接证明服务器关机。历史上针对某台停用机器的忽略决定不适用于当前目标。
