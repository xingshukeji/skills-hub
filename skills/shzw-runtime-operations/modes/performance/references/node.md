# Node.js 的 CPU、内存与 IO 优化

按目标项目声明和实际实例确认 Node、V8、依赖、宿主及容器限制。Workforce 的宿主、Harness 的执行生命周期与公共 .NET 平台分别定位；应用请求慢不表示 Node 事件循环是瓶颈。

## 从证据选择改法

| 观察 | 分清什么 | 可试方向与功能边界 |
|---|---|---|
| 主线程繁忙或交互排队 | CPU 时间、事件循环利用率/延迟及热点；区分计算、同步 IO 与依赖等待 | 先减少重复解析、遍历和序列化；计算热点或无法替换的同步调用阻塞主线程时，再比较已有执行池/worker；可用的异步 IO 优先复用。Promise.all 不能把同一线程的计算变成并行 |
| 内存增长或频繁 GC | heapUsed、external、arrayBuffers、RSS、存活对象与保留者 | 检查重复物化、缓存与辅助集合、闭包/监听、Buffer 和原生资源；不能只看 V8 堆大小判定进程内存 |
| 文件、附件或响应过大 | 真实读写字节、缓冲与背压、关闭及取消 | 使用现有 stream/pipeline 和业务允许的分段，避免收集全部 chunk 后再拼接；保持完整数据、错误传播和持久完成时点 |
| 并发增加却更慢 | 事件循环、libuv 线程池、数据库/远端池、队列与实际在途量 | 在实际拥堵层控制工作，复用当前并发机制；取消等待者不等于底层 IO 已停止，也不能按每层并发值相加估算有效吞吐 |

已有 perf_hooks 可帮助定位事件循环问题，但先确认采集窗口、开销及指标单位；monitorEventLoopDelay 的直方图值按其文档处理，不能当作请求延迟。计时器、连接、监听和任务的自然结束要用生命周期或持有关系证明，不能靠强制 GC 或重启。

## 减少复制时保留所有权

先分清字符串字符数、UTF-8 字节及 Buffer 的视图。Buffer.subarray/slice 可以共享原存储，小视图也可能保留大父缓冲；省去复制后要核对修改、跨请求复用和结束时点。跨 worker 的复制、共享或转移按当前 API 判断；转移可能使原视图失效，池化 Buffer 的底层 ArrayBuffer 也不能直接按独占缓冲处理。

对编码、摘要和文件路径保留原协议与精度，不用 JavaScript string.length 代替字节预算。只有业务需要长期保留独立数据时才复制；复用不能让一个租户、页面或执行改变另一方仍在使用的内容。

IO 流优先使用已有错误传播与背压机制。fetch 等响应体按当前库合同消费或取消，检查连接是否实际归还；读完响应头不能代替消费结束。使用 worker 前比较任务粒度、初始化、传输/复制、取消和退出代价，不为每个小请求创建线程或新增另一套 Runtime 调度。

## 保持代码与验证清楚

让数据来源、正在等待的操作及最终保存结果清楚可见。减少一次重复转换往往比维护自定义池或通用缓存更直接；复杂机制需要实际收益支持。提取函数按职责和生命周期组织，避免为每个错误增加另一套状态或吞掉原异常。

分别验证原功能、相关合法输入、取消/关闭、迟到结果、保存失败、并发及恢复。优化 JSON 或 Buffer 后比较字节、Unicode、顺序与独立所有权；优化批量或流式处理后检查完整输出与部分失败。隔离样例和组件耗时不能声称已证明真实 Runtime 或页面性能。

## 官方依据

- [perf_hooks](https://nodejs.org/docs/latest-v24.x/api/perf_hooks.html)：事件循环与有界计时；按目标版本核对指标。
- [Buffer](https://nodejs.org/docs/latest-v24.x/api/buffer.html)：编码、字节长度、视图及底层存储。
- [Stream](https://nodejs.org/download/release/v24.0.0/docs/api/stream.html)：背压、pipeline、取消与错误传播。
- [Worker threads](https://nodejs.org/docs/latest-v24.x/api/worker_threads.html)：线程用途、消息传输及 Buffer 所有权。

链接是研究入口，不规定项目必须升级到该版本，也不授权新工具安装或全机采样。
