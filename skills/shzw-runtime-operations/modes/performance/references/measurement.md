# 测量结果核验

用于根据性能数字报告改善、选择实现或调整配置。先写清要判断的业务结果、单位和计时范围，再读实际测量脚本。以下检查只针对影响本次判断的疑点，不要求每次采样运行全部工具。

## 确认工作在计时区间内完成

把有效业务量和耗时放在同一次执行中核对。请求已发出、Promise 已创建或返回码成功，均不能单独证明工作完成。异步操作等待原合同规定的完成点；流和迭代器消费到所测范围的末尾；写入按实际回执及必要回读确认。若接口只承诺受理，就报告受理耗时，另行观察完成，不能称为业务完成耗时。

例如，导入计时在 `importer.commit(...)` 返回 Promise 时就停止，随后再等待并检查 4000 行，能够证明最终导入成功，却不能证明这 4000 行在所报耗时内完成。应先等待提交完成，再停止计时；必要回读耗时是否计入由所测用户动作决定。缓存命中是合法目标时保留该测量，并标明它不包含未发生的读取或写入。

保留失败、超时、取消、重试及未完成数量。分别验证结果正确性，不能只数成功状态。发压端先饱和时，吞吐反映的是发压能力；用既有计数和资源证据定位，不把它当作服务容量。

## 核对收益可能达到的范围

用同一业务路径的耗时分解或资源计数解释当前限制。采样用于定位，正式计时另跑并说明差异。尚未定位限制时可以报告已观察到的耗时，但不要据此认定因果或选择长期架构。

对其余工作不变、阶段串行且可相加的路径，若总耗时为 `T`、本次只改变的阶段为 `A`，该阶段加速 `s` 倍后的总耗时应为 `T - A + A / s`。即使完全移除该阶段，也不能节省超过 `A`。例如 1000 ms 中的 100 ms 阶段，即使零耗时，整体也只能降到 900 ms；若报告 500 ms，就要检查缓存、漏做工作、计时范围或同时变化的其他条件。并行重叠、排队和资源争用变化不直接套此公式，需用关键路径及实际完成量解释。

必要时按真实字节量、磁盘或网络带宽、CPU 配额检查数量级。超出估算范围是重新核验的线索，不直接判定造假或产品缺陷。无法排除其他因素时保留观察值，将收益归因或方案优劣标为未确认。

## 保持比较公平

核对两侧是否使用目标实际支持的构建方式、批量与事务配置、连接池、缓存状态和数据。若一个候选只是配置不当，先在现有授权内调整后再比较；无法调整时，只报告当前配置差异，不据此判定实现本身更优。

共享负载、预热或环境漂移可能影响结论时，交替执行两侧并保留各次结果。根据实际波动补样，报告样本数、中位值和范围；差异小于波动时写明尚无可辨别收益。单次粗测只说明该次观察，不扩大为稳定结论。
