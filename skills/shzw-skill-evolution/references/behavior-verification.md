# 技能行为验证

验证技能是否改变了有价值的实际行为。先固定原任务输入和判定依据，再改内容；预期结果不能混入评估者的原始请求。

## 准备可比较的任务

保留修改前的完整技能、直接路由与依赖资源。基线是本次实际要改的内容，不一定是 Git HEAD。记录评估环境、模型设置和加载方式；不同条件的结果不能当作纯技能差异。

从真实纠偏中抽取原始请求和当时已经确认的前文，去掉秘密和客户信息。后续补充仅用于判断：原任务遗漏、方向修正、新需求、环境限制分别标识。对源码或工具任务准备隔离工作目录、足够的真实合同和可运行入口，不能让评估者靠猜私有项目完成。

区分改写回归、候选选择和最终检验。改写时已看的原题用于复现；比较后用于挑选候选的材料已参与选型，不能再当最终未见案例。另留未参与编写和选型的相邻任务，在基线与候选两个条件下都执行。任务少时不报百分比；说明样本与适用限制即可。

同一作者读过反馈后试写，或在“共同输入”中提示已知错误，可以帮助校准，但不能证明执行者自行发现了该问题。原请求、当时前文和工具事实放执行目录；后续纠偏、预期答案和评分材料放评判侧。变化后另存一组，不覆盖先前失败。

## 按要证明的能力执行

| 要证明的能力 | 直接证据 | 不能替代的证据 |
|---|---|---|
| 能选对技能或保持原任务 | 原始请求、实际候选目录、真实选择和加载记录 | 作者看描述觉得匹配 |
| 能区分相近错因并修对位置 | 相同失败表象下的不同规则、加载返回和合同；实际修改与应保持文件的差异 | 输入直接给出“方法错误”或“只是环境”，回答复述分类 |
| 能完成开发或运维动作 | 文件增量、实际命令或工具调用、业务后置条件 | 计划、伪代码、正确口号 |
| 能审出业务问题 | 可达入口、触发、违反规则、责任代码及反证 | 命中关键词、泛化检查表 |
| 能接续并减少无效交互 | 保留原约束，执行剩余工作；记录重复询问、无效停顿和遗漏 | 最终回答更短、工具调用更少 |
| 能克制无关流程与错误归因 | 相邻合法场景、只读请求、新目标或环境故障仍正确处理 | 只测会触发的正例 |
| 能完整交付技能资源 | 完整目录闭包、脚本运行、实际入口读取及对应提交或制品核对 | SKILL.md 存在、本机目录相同、目录数量下降 |

为改变的行为选择合适对照：修改前与修改后，或无技能与有技能。两边使用相同业务输入与工具条件，互相隔离执行结果。已看过判定答案的执行者不能算独立验证；结构测试与作者走查分别报告。

需要独立代理时，先遵守当前任务的委派授权。授权不足时继续可做的检查，并说明未取得独立行为证据；不能通过另开聊天、后台 CLI 或外部模型接口绕过。通常无需固定轮数；差异不稳或有具体回归疑点时才补测。

## 检查结果和过程

先看业务产物与后置条件，再看执行过程中的假设、加载和失败。把失败归到输入、选择、方法、知识、工具、环境或执行本身。单次偶然成功不能证明稳定，单次模型失误也不能直接证明规则有缺陷。

诊断任务同时检查改动和克制：错误方法应在唯一来源修正，旧副本或错误入口应修对应消费路径，正确规则应保持。用原始轨迹和实际文件判断，不按是否写出分类词评分。证据不足时应保留未确认，不能把超时自动解释成环境故障。最后核对原业务结果，不能只交一份技能修订说明。

计数时区分：必要的业务选择、权限请求、用户新增要求，与可自行查证却重复询问、已授权却停顿、原目标遗漏后的返工。只减少后一类交互；不得为了少问一次而猜测关键业务决定或越权。

## 相邻判例

- 已要求“页面操作完成后再确认结果”，只验 API 就宣告完成：原验收遗漏，应补原路径并查方法。用户后来要求移动端，则需对照原范围判断是否新增，不能自动追认。
- 已批准邮件仅发送，后续说“请实现”：承接最新方案。更早曾要求收件箱不代表现在必须保留，方向变化与执行遗忘不同。
- 列表、详情与目录共用身份，修恢复只查目录：应从该身份的消费者检查遗漏。相邻的主身份隔离可能是正确保护，不能取消它来修局部故障。
- 技能明确要求保留草稿，执行者没读到：先查发现和加载；已经读到但没执行则先纠正动作。不能只增加“务必保留草稿”的重复文字。
- 服务不可达而技能正确指向该服务：环境前提未满足。若技能仍指向已退役入口，则有可定位的资源维护缺陷。
