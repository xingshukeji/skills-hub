# 技能诊断与进化

让技能在真实任务中减少遗漏、重复解释、无效停顿与错误操作。改进单位是导致错误决策的具体方法或入口，不是每次反馈都新增一个 skill。

## 何时进入

用户明确要求审查、修正或沉淀技能时进入。实际任务中出现下列证据，也应检查项目是否已授权主动改进：

- 用户再次指出原要求已有的业务、消费者或验收条件，执行却遗漏；已授权工作反复停在方案或“是否继续”。
- 多个技能对同一结果给出冲突步骤，或把任务推到不拥有结果的项目。
- 已选择并读取技能，仍只能给通用清单，无法定位当前业务判断、真实入口或下一项有效行动。
- 描述吸引无关任务、遗漏本应适用的请求，或正文调用已失效的资源、接口和脚本。
- 技能要求多余流程，使局部工作依赖无关环境、审查或用户确认；或跳过原任务必需验证。

一次明确反例即可证明某条规则有错。多轮纠偏只提供调查线索，不能单凭次数认定技能失败。新需求、方向变化、服务故障、缺少工具权限和未遵循已有规则，应先分别归因。

明确要求本轮只讨论、先理解或不修改文件时保持只读。业务审查中的产品源码只读边界继续有效；技能维护是否可写，按它自己的已有授权判断。主动改进需要当前请求或目标项目明确的长期授权，本技能不自行授予权限。授权范围内直接完成最小修正及验证，不让用户重复批准同一工作。

## 确认哪里失效

只恢复相关原始请求、必要前文、当时可得事实、实际动作和后续纠正。先写出应有业务结果，核对所选技能和入口是否匹配、实际加载路径和版本及相关资源。新要求不要提前放入原输入，旧副本失败不能归到当前源码。

涉及本平台的技能，额外核对它是否帮助做出了正确选择：现有 XRain 能力能否直接用、还缺什么业务配置或逻辑、Workforce/Harness/业务应用分别负责哪一步、目标实际版本是否支持。把技能正文与实际调用、返回和消费者对照；只增加“读取项目入口”或平台名称，不算补齐方法。

用户反复指出的“已有能力又造一套”“接口结构靠猜”“平台做完却业务没通”“内部解释堆到界面”“简单动作要求多轮确认”，分别追到能力判断、调用合同、原业务验收、可见内容与授权接续。只修有证据的错误；不要把某项目的固定发布源、安装形式或测试环境推广到所有项目。

沿下表确定因果；同一现象可能有多个原因，但每个原因必须有证据。

| 证据 | 判断与修正位置 |
|---|---|
| 原请求与描述匹配错误，或项目入口指向错误方法 | 修描述、调用策略或最短路由；正文可保持不变 |
| 规则已加载却要求错误步骤、遗漏必要分支或缺少可操作判断 | 修改该方法；用真实入口和可观察结果替换空泛要求 |
| 规则正确清楚，实际执行没照做 | 先纠正执行；只有能定位被埋没、矛盾或加载过重等原因时才改技能，不能追加同义禁令 |
| 方案、审查、实现、产品知识或治理互相抢职责 | 让一个入口负责用户结果；其他知识按需引用，只保留真实独立的方法 |
| 专题、脚本或调用合同已过时 | 在知识或工具源修复，并检查直接消费者；不能用更多提示词掩盖接口错误 |
| 当前请求只是继续既有工作，却重新规划或丢失约束 | 修恢复与接续方式，保留已确认目标及授权；不是新增一个“继续任务”技能 |
| 必需资源缺失、工具拒绝或环境未准备 | 记录具体前提，使用受支持替代路径；只有技能错误描述了这些前提或恢复方式才修改 |
| 用户改变目标，或新增原范围不存在的结果 | 更新原任务范围，不追认旧技能有缺陷；新目标只有可复用方法缺口时才进入技能设计 |

结论限定到实际失败的环节。只有核心职责无法完成、必需资源不可用且没有受支持替代，或核心指令与有效约束冲突时，才判定该技能在当前场景不可用；其余环节可继续使用。证据不足时指出最小待验证条件，不宣布整个技能失效。

## 在原任务中主动修正

若错误方法正在导致越权、数据损失或重复失败，停止相应步骤，回到现行契约和已授权替代方法。其余业务工作继续。一般方法缺陷在当前交付过程中顺带修正；不能把原业务任务换成一次全库技能治理。

确定唯一所有者：专业方法归技能；产品规则归项目契约和测试；服务操作归 Runbook；入口选择归 AGENTS；授权与任务生命周期归工作流。只因修正文案不读取全部治理面。实际涉及治理关系时才使用 `shzw-workspace-maintenance`。

先删除冲突、重复和无效步骤，再补缺失判断。根据失败形式选择表达：容易选错时写清触发条件；步骤缺失时给简短操作顺序；产物缺项时补实际模板；业务判断不稳时提供一个具体判例及适用边界。保留模型对普通实现细节的选择，不把历史事故变成通用强制清单。

只有既有入口确实无法承载独立任务时才新增技能。合并或拆分先核对任务结果、触发、资源与消费者，再移动完整目录内容和入链；保留有用的产品知识、脚本、示例与声明。不要通过压短正文丢弃完成工作所需的知识。

在来源仓库修改，随后更新当前任务命中的完整安装副本与直接路由。未修改源码却只改消费副本，或只改 description 却保留冲突模式，均未完成。目录、注册表或后台监控不能代替真实方法。

## 验证是否有帮助

实质改写前保存当前内容基线。按[行为验证](references/behavior-verification.md)选择能复现原失败的任务，并加入相邻反例及未参与编写的案例。让评估者完成真实文件修改、查询或审查；只回答“接下来怎么做”只能证明决策表达。

检查业务结果、责任方、关键动作、必要交互、外部影响和证据。平台相关改写至少选择命中能力的业务案例；通用代码小例和文本规则检查不能证明真实平台选型、权限或业务交付已经改善。能删除一次多余确认却漏掉原验收，不是改善。复查完整执行过程，不能只看最终措辞。结构检查通过后，再报告行为证据；未做独立执行时明确限制，不宣称激活率或对话轮数已改善。

修正通过后回到原任务，完成其余已授权结果。只说明与用户有关的改进和实际限制；不创建每次进化日志、用户画像或第二套任务台账。后续真实任务暴露回归时更新同一规则。

需要选择改写和评估方法时，可读[开源方法取舍](references/open-source-methods.md)。这些资料是研究来源，不授予额外执行、跨聊天、子智能体或外部写入权限。
