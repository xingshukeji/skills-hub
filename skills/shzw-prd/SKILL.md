# 产品需求文档

为首次接触项目的人和智能体写清需求，让读者能理解业务、查到规则并据此开发和验收。使用[固定模板](assets/prd-template.md)组织内容，按下面六步完成写作、审阅、修订和反馈验证。模板固定阅读顺序与必要问题；平台事实仍从责任项目查证。

先判断授权：仅理解或只审阅时，给出理解或定位到原文的问题，不改 PRD。已授权编写、改写或延续修订时完成全文和验证。用户要求先做样板时，只精调选中的功能，按约定取得样板反馈后再固化方法和推广；已经确认的样板不重复询问。没有这种要求时，普通写作不增加审批。多步不自动授权委派或跨聊天，也不要求固定轮数。

## 1. 确定范围并查证事实

确定读者、产品、用户目标及必要前文。按目标项目入口定位产品契约、当前设计、类型、元数据和测试；区分已确认要求、当前实现或部署证据、未决事项。一个独立用户目标可以是一份 PRD，不按源码文件机械拆分，也不把企业定制混入公共功能。

产品规则由责任项目的正式契约维护。需求改变时先更新该来源，再同步 PRD；语言整理不得改动规则。核心行为尚未确定且影响实现、权限或业务结果时，先查已有约束，再提出具体选择及影响。没有决定就标明受影响范围，不能靠写作补成既定规则。普通表达和结构选择由作者完成。

涉及 XRain/Workforce 时，沿真实链路核对 Workforce 的用户入口、XRain 的身份、元数据、授权和调度、Runtime 的定义与执行，以及业务服务的结果。只引入实际参与的组件。普通 Task、定时任务和一次性检查分别核对，不能因名称相近共用权限或超时规则。参见[平台判例](references/platform-examples.md)。

## 2. 按读者任务安排结构

按[固定模板](assets/prd-template.md)建立骨架：场景与定位、流程、角色与动作、字段、执行与状态、权限、异常恢复、组件协作、实现差距、未决事项、验收及依据。先用场景解释“谁要完成什么”。没有相关内容的可选章节可删除，相邻短节可合并；不要留下占位文字，也不为凑章节制造功能。

字段表说明取值与约束，角色表说明操作资格，执行章节解释时机和状态。复杂功能在执行章节增加配置、周期或人工处理等相关小节。普通 Task、定时任务及邮箱不共享一套业务字段或时限。正式元数据、文件位置及篇幅限制遵循目标仓库，模板不另设统一字数。

给每条规则确定一个主要说明位置。图负责概览，正文补条件和例外，验收给出具体输入与观察；避免功能表、动作表和总结逐句复述同一规则。关联功能链接其详细说明，同时保留本页独立阅读所需的前提。长篇 PRD 提供就近导航；技术详表只放确实需要逐项查询的内容，不复制一遍主文。

## 3. 写出完整初稿

沿核心动作回答：谁在什么条件下输入什么，系统如何处理，状态或数据怎样变化，读者看到什么，以及失败后怎样继续。

- 字段写清含义、必填性、取值、默认值、来源、校验、生效时间及修改限制。已能查到的规则不能用“以接口为准”代替。
- 权限结合动作和状态说明；分别判断可见、可操作、保存、触发及业务成功。不要只写“按权限判断”。
- 失败按具体环节说明原因、已确认结果、保留内容和下一步。区分拒绝、部分成功与结果未知；不假定回滚或安全重试。主文保留用户理解和处理所需内容；错误码及实现路径放到必要的相邻详表，不重复主文。提示列注明建议，已有文案及当前操作限制明确标注。
- 定时或自主执行核对执行身份、定义与模型、版本、重叠与停机、人工处理、超时、改派和历史访问；使用具体时序例子解释真正相关的规则。
- 需求、实现差距和待决定事项应容易辨认。使用统一标注和集中说明，避免在每段末尾重复免责声明。无证据的指标、默认值和发布计划不能补造。
- 用户要求 SVG 或图有助理解时提供可放大的图，文字保留图中省略的条件；不把内部架构术语直接用作产品界面文案。

## 4. 从头审阅并精简改写

写完后，单独按首次读者的阅读顺序审一次，不能以“字段齐全”或文档检查通过代替。审阅已有 PRD 时可从此步定位问题，再回前面查证。依[反馈闭环](references/feedback-loop.md)把具体问题、影响、改法和复核结果留在当前任务已有记录或临时证据中。

1. **重复：**找出反复出现的背景、规则、权限提醒和失败说明；合并到主要位置。保留有用途的概览和验收例子，不为缩短而删除条件或例外。
2. **顺序：**概念先解释再使用；从场景进入规则。拆开混有目标、现状、实现细节和作者自我说明的段落。
3. **表达：**用读者熟悉的业务词，明确主体与动作；拆开多重条件和过长句子。将“事实所有者、获权主体、消费闭环”等内部简称改成具体的人、服务和结果，必要代码标识保留。
4. **版式：**表格只比较平行信息；格子塞入多段论述时改用段落或拆表。合并相邻重复章节，删除空泛标题和无信息的小结。
5. **可用性：**读者能否找到允许值、知道失败后保留什么、判断下一步由谁做？跨页链接是否只是追溯，而非理解当前功能的必经跳转？

先修影响理解和判断的问题，再做文字润色。审阅结论给出具体位置、读者受到的影响和处理方式；不只说“可读性不足”。不设统一行数或压缩率，篇幅减少不是完成标准。

## 5. 核对语义、图示与交付

对照修改前内容和权威来源，逐项核对范围、角色、字段值、默认值、条件中的“且/或”、否定、例外、状态顺序、失败恢复和实现差距。被合并或移走的独有规则必须能在新位置找到，不能用关键词仍存在证明语义未丢。

从正文走一条正常场景，再走与功能有关的失权、状态变化、部分成功或未知结果场景；能据文判断结果才算通过。渲染受影响 SVG，检查可读性和图文一致；检查引用、章节锚点和项目要求的文档校验。语言审阅、作者走查、独立读者评估及产品运行验证分别报告。

本轮发现规则丢失、读者无法判断或图文冲突时，回到对应段落修订，再复核受影响场景。没有未解决的实质阅读问题、语义回查通过且所需决定已经取得，才结束该轮；仍有阻塞决定时明确哪些内容不能用于开发验收。长期文档按项目 StructureContract 放置。

## 6. 将反馈写回方法并验证（RSI）

RSI 在这里落实为“生成—审阅—改写—复核—反馈—方法修订—再验证”的闭环。先修当前文档，再判断原因：规则缺失或模板诱发重复才修方法；未遵循已有步骤先纠正执行；新增需求更新任务和产品来源。不要把每次措辞修改都追加成通用规则。

用户认可样板后，提取已证明有效的结构和判断方法，更新本技能或模板的原位置，不复制业务全文、固定业务默认值或历史过程。沿技能诊断与进化的授权与验证规则，在来源目录修改并更新本次命中的完整消费副本。

用相同任务输入和事实重新生成一份实际稿件，对照已确认样板检查关键规则及原问题是否再次出现；再选一个未用于本次改写的相邻功能，检查模板是否强塞无关字段或规则。样稿保存在允许的临时位置，未确认前不覆盖正式 PRD。检查失败就修对应方法并重跑受影响案例；作者复写只能报告为作者验证，不能称为独立测量。具体判据见[反馈闭环](references/feedback-loop.md)。

多功能任务在样板及方法完成后，仍须在已授权范围内逐份审阅，核对目录覆盖和剩余问题；不得只抽查一篇或批量替换后声称全部通过。技能已能完成任务时不重复启动一次技能升级。
