# PRD 固定框架与可组合版式

此框架固定交付前应回答的问题，不固定所有功能的章节名和顺序。先遵循目标仓库的正式元数据、文档位置及用户指定格式；再按实际业务选择、组合下面的版式。示例仅说明结构，不提供平台业务规则。交付前删除使用说明和占位内容。

## 每份都要交代

1. **目标与范围：**谁遇到什么事，使用本功能完成什么；哪些相近动作不属于本功能。先给一个具体场景。
2. **使用与结果：**相关角色在什么条件下输入或选择什么；系统或其他组件做什么；状态、数据和用户可见结果如何变化。
3. **规则与字段：**需要决策或校验的字段，说明含义、必填、取值、默认、来源、限制和生效时机；无关联字段不制造字段表。
4. **权限与异常：**按实际动作说明可见、修改、执行和历史访问；发生拒绝、部分成功或结果未知时，说明保留什么、如何核对和继续。不适用的情形无需强写。
5. **协作与差距：**只说明真实参与的组件和数据归属；区分已确认目标、当前实现或运行证据、会影响实施的未决项。
6. **验收与依据：**提供可观察的正常和相关反例，以及可追溯来源。用户要求 SVG 或图有助于理解时，提供实际可放大的图。

这些是检查问题，不是六个必须照抄的标题。章节可以调整、合并或分拆；不能因为调整版式遗漏适用规则。指标、版本计划或日期仅在本任务需要且有依据时填写。

## 选择和组合正文版式

| 读者主要想知道 | 适合优先采用的版式 | 组织时注意 |
|---|---|---|
| 从哪里完成几个不同动作 | **按操作或对象**：每个动作旁说明相关字段、前提和结果。 | 区分可独立选择的动作与实际的先后依赖；不要把分支画成必经步骤。 |
| 一个事项何时进入下一状态 | **按状态或时间**：先说明状态及触发，再说明变化后的权限、异常和后续动作。 | 固定时点、先后、重叠和恢复条件；状态名称取产品事实。 |
| 设置、入口或权限影响什么范围 | **按角色或作用范围**：分别说明本人、设备、租户或其他真实范围。 | 写清设置生效边界、身份变化及是否改变业务授权。 |
| 能力怎样与其他服务协作 | **按参与方和交互**：用一个业务场景串起实际的输入、责任及结果。 | 不把所有服务塞入每个功能，也不把组件图代替用户动作。 |

它们不是互斥的功能分类。例如同一 PRD 可以按操作分节，在某一动作中用状态表说明等待；也可以按状态讲主线，在附近给字段表。名称、顺序和篇幅由读者需要决定。

## 两种应用方式

- **周期执行：**“设置安排 → 启停 → 到期领取 → 运行或等待 → 结果与历史”适合按状态和时序组织；配置字段靠近设置，改派和人工处理跟随相关状态。
- **个人邮箱：**“管理账户、阅读、AI 协助、编辑和保存草稿”可分成并列动作；账户与草稿各有字段，AI 可不使用。保存未知需回查原邮箱，不能套用周期运行的超时或改派规则。

以上例子不能替代责任项目的现行产品契约和源码；新功能不必归入其中任何一种。
