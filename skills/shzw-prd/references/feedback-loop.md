# PRD 的 RSI 反馈闭环

让每轮反馈修正实际产物，并验证方法能否在下一次写作中复用。按当前请求和已有授权执行；用户要求先确认样板时遵守该顺序，普通局部改写不增加批准步骤。

## 一轮怎样完成

| 步骤 | 实际产物与检查 |
|---|---|
| 固定输入 | 读者、原请求、已确认产品规则、实现事实和旧稿。用户后来新增的要求单独辨认，不假装原请求已有。 |
| 生成初稿 | 用固定框架选择适合本功能的版式，形成可阅读全文并提供必要 SVG；不只给提纲或检查计划。 |
| 阅读审查 | 检查标题是否说清具体内容，有顺序的操作是否使用 Markdown 有序列表；逐段指出重复、长段、术语和缺失条件，检查并列动作是否被误写成必经流程。说明首次读者会在哪一步误解或无法决定。 |
| 改写 | 每条问题对应实际修改；合并的独有规则须能在新位置找到。 |
| 语义复核 | 对照旧稿和正式来源检查角色、取值、默认、且/或、否定、例外、时序、失败及恢复。再走正常与相关反例，渲染图示。 |
| 接收反馈 | 核对用户指出的具体阅读问题；用户认可结构不等于产品已实现或所有业务规则均获新授权。 |
| 修订方法 | 有证据的可复用原因才修改技能或模板的原位置，再用实际稿件验证；其余问题在当前文档修正。 |

当前任务需要记录时，用已有活动记录或允许的临时证据保存下面四项；不为每轮创建长期日志或第二个任务台账。

| 具体问题与位置 | 对读者的影响 | 实际改法 | 复核结果或剩余问题 |
|---|---|---|---|
| 同一权限在角色表、动作表和正文重复 | 不知道哪处是完整条件，后续修改易不一致 | 角色表给基本动作，复杂历史条件集中说明，其余引用 | 用有资格、失权、仍有另一角色三个情形核对，不只检查关键词 |

## 哪些反馈应改方法

- **方法缺项：**原技能只要求字段齐全，没有要求读者顺序审阅，导致重复表格。补审阅步骤与模板职责，不再追加一套同义功能表。
- **模板诱发问题：**一条规则必须在多个固定格子各写一遍。调整模板，给规则一个主要位置；概览、条件和验收各有用途。
- **执行遗漏：**技能已要求检查“且/或”，改写却放宽了权限。先修稿并重新核对；除非发现指令被冲突或过量内容埋没，不再增加同义禁令。
- **新需求：**用户改变默认时限或增加角色。先更新任务及产品规则，不能据此认定旧写作方法有错；具体默认值不固化进通用模板。
- **证据不足：**服务不可用或接口事实缺失。标清受影响范围并继续可做部分，不能通过文案把未知改成已实现。

## 方法修改后怎样验证

1. 保留修改前的完整技能和相关样稿，固定相同的任务输入与事实范围。框架提供必要问题和可选结构，样稿是比较对象；不能复制样稿后声称重新生成成功。
2. 使用修订后的完整技能，从输入重新写一份实际稿件。比较是否保留关键规则，是否再次出现原阅读问题，以及字段、步骤、图示、异常和验收是否各司其职。措辞相同不是要求，篇幅缩短不是通过标准。
3. 选择一个未用于本次方法改写的相邻功能，形成实际草稿。检查能否选另一种结构，以及不适用章节能否删减、业务差异是否保留；例如普通 Task 的读取资格不套用定时历史规则，邮箱保存结果未知不等于可以再次保存。
4. 加入适用边界检查：只读审阅不改文件，已认可样板不重复问，用户要求先一篇时不批量改全部。新问题回到对应方法修正；只重查受影响案例。
5. 分开报告用户对样板的认可、作者复写、独立执行和运行测试。没有独立执行时不能宣称稳定提升、成功率或减少了多少轮；已有评估工具能覆盖的部分复用它，不为一次写作增加运行路由或后台评估服务。

需要比较开源方法时，固定其来源版本，使用同一任务输入和事实形成可阅读的实际稿件，再比较具体得失。平台事实和用户授权始终来自本项目；不因外部方法要求而创建工单、安排访谈、调用代理或编造指标。样稿由同一作者先后写成时说明局限，不能称为独立盲测。

## 何时可以推广

样板没有未解决的实质阅读问题，独有规则未丢，必要产品决定及用户要求的确认已经取得，方法复写和相邻案例没有发现回归，才在原授权范围推广。需要产品决定而未解决的内容明确标注，不能把它计为可直接开发验收的完整需求。

推广后发现同类问题时，回到原方法和模板修正，再核对受影响文档。每篇仍逐项审阅；不能以样板通过代替其余功能的事实核对。
