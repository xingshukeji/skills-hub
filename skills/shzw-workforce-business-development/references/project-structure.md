# XRain 二次开发项目源码结构

产品事实：XRain、Workforce 与智能体 Runtime 分别由各自产品维护；业务和制品由目标项目维护。本专题规定二开项目源码的默认组织方法，不改变平台包格式或目标环境能力。

## 使用范围

初始化、规划或调整 XRain 二开项目时，先识别业务实际使用的平台资源、函数、服务、客户端及智能体，再按其交付目标组织源码。新项目以本结构为默认；已有项目先识别入口、生成器、消费方和稳定资源身份，按本次授权增量迁移。不存在的能力不创建空目录。小项目可保持较少层级，但 README 必须说明源码、构建入口与实际交付目标。

目录是本地组织方式，不是应用包协议，也不自动安装、加载或授予权限。通用平台能力、Workforce 宿主和 Runtime 的实现留在对应产品；二开项目消费公开能力并维护业务差异。

组织方法参考 Salesforce DX 将元数据与代码纳入本地项目并按包分组；[本地包目录不等于目标环境中已安装的包](https://developer.salesforce.com/docs/platform/sfdx-dev/guide/sfdx-dev-ws-mpd.html)。Salesforce 的[源码跟踪](https://developer.salesforce.com/docs/platform/sfdx-dev/guide/sfdx-dev-source-tracking.html)依赖目标环境支持，不代表 XRain 已提供同样能力。

## 默认目录

```text
<project>/
├── README.md                    # 开发入口、源码与交付导航
├── platform/                    # 发布到 XRain 的业务资源源码
│   ├── app-package/             # 对象、字段、权限、编排等包源码
│   │   ├── source.json          # 小型应用可直接维护完整包源码
│   │   ├── objects/             # 需要分片时，按对象组织定义
│   │   ├── permissions/         # 需要分片时，组织权限与共享规则
│   │   ├── orchestrations/      # 平台编排及其定义
│   │   ├── triggers/            # 记录事件绑定
│   │   └── imports/             # 平台导入相关资源与脚本
│   └── functions/               # 平台函数的可编辑源码和适用合同
│       └── <function>/
│           ├── index.mjs        # 入口名称按项目工具链选择
│           └── contract.json    # 该函数需要时的输入输出合同
├── agent/                       # 需交付的智能体业务定义和文件
│   └── <agent>/
│       ├── definition.json      # 可移植定义或由唯一源码生成的定义
│       ├── instructions/        # 指令和工具声明的可编辑源码（如需）
│       └── workspace/           # 项目需提供的工作区文件
├── applications/                # 业务应用；按需要包含服务和客户端
│   └── <application>/
│       ├── backend/             # 业务服务、工具处理器与宿主装配
│       ├── frontend/            # Web 页面和业务插件
│       └── miniprogram/         # 微信小程序或其他独立客户端
├── src/shared/                  # 多个实际消费者共用的源码
├── scripts/                     # 项目构建、导出和开发辅助入口
├── tests/                       # 平台、服务、客户端及其合同的测试
├── config/                      # 非秘密的配置示例（如需）
├── examples/                    # 无真实业务数据的示例
├── .artifacts/                  # 被忽略的本地构建输出
└── .local/                      # 被忽略的本机配置和临时状态
```

树形图列出可选位置，不要求为每个项目创建所有目录，也不要求使用 Node.js、React 或特定构建器。只有一个应用包时 `app-package/` 可直接承载它；多个包各自使用稳定的子目录和明确入口。文件扩展名与工具由项目决定。项目已有等价结构时，在 README 建立对应关系，不为统一名称打断在途工作。

`app-package/source.json` 是小型项目的完整源码示例。复杂项目可维护可编辑片段、代码生成器与显式组装入口，生成符合当前平台合同的一份完整包源码；不要把片段当作新的平台包协议。对象、字段、权限、编排与版本身份沿原资源保持稳定。已发布版本不可原地替换；历史升级生成所需的定义和消费者继续保留。具体包合同与操作见应用包技能的[编写方法](https://github.com/xingshukeji/skills-hub/blob/main/skills/shzw-xrain-app-package/modes/authoring/GUIDE.md)。

## 源码到实际消费者

| 源码 | 输出与使用者 | 必须区分 |
| --- | --- | --- |
| 平台包定义、平台编排和 Trigger | 组装完整包源码，构建 `.appkg`；平台按目标版本安装并执行所含资源 | 本地构建、发布、安装、应用资源选择和原用户可用是不同结果；包不能承载任意项目文件 |
| `platform/functions/` | 以入口及依赖生成平台可执行函数源码和适用合同，按包或租户来源交付 | 普通编排和函数使用各自受支持的调用合同；受保护纯函数不能访问 SDK、网络、记录或环境时间和随机数 |
| `agent/` 中的定义 | 导出或生成可移植定义，由定义管理入口导入或更新 | 定义、工具声明、实际处理器、使用资格及业务授权分别生效；在线定义按目标版本与修订维护 |
| `agent/` 中的工作区文件 | 经目标支持的文件交付方式放入实际 Runtime 工作区 | 项目模板或选用的完整技能目录不等于运行中的 `cwd`；保留目标已有文件、定义和会话 |
| 应用服务与客户端 | 由项目现有工具构建宿主、Web 或原生客户端制品 | 工具处理器在实际业务服务或其他明确提供者运行；客户端不能替代服务端授权或平台规则 |
| 多消费者共用源码 | 由各消费者的构建过程引用或打包 | 一份源码可以进入多个制品；核对实际依赖图与环境约束，不复制正式业务算法或将服务端敏感逻辑误带入客户端 |

平台函数源码只维护一份。包受管函数由包源码组装引用或生成平台资源；租户可维护函数通过受支持管理入口单独建立或更新。同一个函数不要为两种交付方式各维护一份可编辑算法。项目须明确函数入口、依赖及适用合同的位置，生成物不作为第二个手工编辑源。普通函数、编排、导入阶段和受保护纯函数的执行环境不同；不能从本地 JavaScript 能执行推断平台支持相同依赖。平台函数及调用语义见[自动化](automation.md)。

平台支持包内 `BizOrchestrationFunction`，但包受管源码在应用入口只读。租户需要维护函数时，按实际平台合同使用租户可维护来源；不要将包受管源码说成可原地编辑。源码、函数版本、应用关联及当前选版是不同事实。安装包或更新函数源码不自动证明应用已选用版本。目标版本是否支持具体受保护调用、函数合同及初始化方式须实际核对。

项目的基线源码与租户允许修改的线上配置也可能不同。新增租户使用已交付的明确来源和目标配置；更新已有租户前读取实际来源及选版，按项目合同处理差异，不在启动或普通升级时静默覆盖租户修改。跨租户自动同步、双向差异跟踪或冲突合并仅在平台和项目明确支持时使用，不因目录存在推断能力。

工作区中的项目业务指令、示例与选用的技能按其原所有者维护；通用技能从其正式来源取得完整目录，不在业务项目发明另一份规则。每项指令、工具声明或定义字段只设一个可编辑事实源，其他副本由现有生成或同步入口核对；不同字段可以由不同源码持有。运行会话、员工私有工作区、凭据、真实客户资料、日志、依赖缓存及生成物不作为项目源码提交；已获准的特定例外按项目入口执行。

## 新租户接入

按项目实际交付物和目标版本选择步骤：

1. 安装所需的公共依赖与业务应用包，并关联实际应用。读取安装结果和目标资源，不把源码目录当作已安装资源。
2. 对包受管函数，核对包内函数来源、可用版本和目标应用关联。对租户可维护函数，使用受支持的管理入口建立函数来源并提供构建后的源码及适用合同。需要的版本由来源管理入口创建。
3. 在实际应用中关联并选用函数版本，提供项目需要的非源码环境配置。角色、成员、密钥和业务数据使用各自受支持的入口，不写入源码或构建包。
4. 通过原业务身份核对应用准入和代表性业务动作。分别确认平台资源、函数版本、宿主、定义和工作区均为实际使用的组合。

上述是目标流程，不表示平台已提供一条命令自动完成全部步骤。目标缺少某项能力或尚未取得必要授权时，只报告相应缺口，不以文件已生成代替安装和使用结果。

## 从修改到生效

1. 修改平台对象或包受管规则：更新包源码，按平台合同构建新版本；安装或升级后核对实际资源。业务数据与租户可配置值按原合同保留。
2. 修改可维护函数：更新同一函数源码与适用合同，验证并生成可执行输入；按实际授权更新目标来源、创建版本、试算及在应用中选版。函数选版不改变历史业务记录。
3. 修改服务或页面：构建并交付对应宿主或客户端；是否同步更新平台包、函数或定义由实际合同差额决定。
4. 修改智能体指令、工具声明或工作区文件：分别通过定义管理和文件交付入口更新；用实际会话核对工具处理器、工作目录和业务结果。

开发构建可验证源码及其直接消费者。发布、目标租户写入、部署和权限变更仍按用户已授权的目标与操作执行。示例不声明存在通用的一键发布或回拉命令；优先使用项目和平台已经支持的 CLI、SDK 或管理接口。

## 采用和迁移时的验证

- 先用一个真实业务动作画出源码 → 构建输入 → 制品 → 安装或装配 → 执行者 → 结果。例如平台报价函数由业务服务调用，记录由平台保存，页面与智能体消费同一结果。
- 核对现有包 ID、资源 ID、函数 key、引用、不可变版本及其直接消费者；更名目录时同步构建脚本、导入路径、公开导出、工作区交付和测试。历史业务数据、租户配置和在途任务保持原样。
- 验证生成输入和必要制品、函数合同、受影响测试以及原业务入口；需要新租户安装时核对目标版本、原身份和所选函数版本。仅生成文件或测试一个组件不能证明其他制品已生效。
- 相邻场景：纯平台应用只需平台源码与测试，无需创建智能体或客户端目录；已有项目只修一个字段时只改原所有者，不以套用目录标准为由搬迁整个仓库。
