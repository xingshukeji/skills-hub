# 分开核对基础产品与目标项目

本方法为业务任务拆分提供依据。当前需求决定要取得什么结果；基础产品的适用能力决定哪些机制可复用；目标项目成果只有仍适用且被本期采用，才能减少剩余工作。下面保存查找与判断方法，不维护实时功能清单或项目完成状态。

## 先确认本期依据与采用决定

定位用户最新确认、原始需求文件及对应评审。区分已经确认的业务选择、尚在评审的设计、旧验证方案和实际交付事实。需求文件没有链接时可按名称引用；内容未读到时不能宣布范围已核实。

对可能影响拆分的成果，分别回答四个问题：它是否存在，是否符合当前需求，本期是否采用，是否已有适用的使用证据。源码与测试回答的通常只是前两个问题的一部分，不能代替用户的采用决定。

采用依据可以来自当前用户决定、仍有效的设计与实际持续使用，不要求为每项现成功能另行索取确认。仅在采用判断确实会改变本次范围、且现有依据不能确定时，澄清该差额；其余已确定工作继续。

例如用户确认铵帮旧 UI、计算、特价、成交和报表只是验证、本期整体重做，这些实现应作为经验材料，不作为新任务已完成的部分。新 E-R 图仍在评审时，不能把图中的全部对象直接发成建表任务。已确认的排除项则立即生效，不必等整份模型定稿。

## 第一次：不计目标项目，核对基础产品

先从项目入口明确本次目标。例如要做铵帮销售助手，本次基础产品核对不包含铵帮。公共能力应在其产品所有者中找到依据；铵帮的包装页面或业务服务只能说明消费情况，不能单独证明它是公共产品能力。

公开能力按 SDK、接口、维护界面和受支持的产品说明核实；有源码时查实现、类型与相关测试。没有私有源码时使用公开接口、产品界面与有效操作结果。业务应用未提供某个入口，不等于平台没有入口；只有实际角色和使用方式确实需要业务内入口时，才形成业务交互工作。只核对会影响当前任务边界的能力。

| 本次需要 | 先查什么 | 如何影响任务边界 |
| --- | --- | --- |
| 人员进入应用并办事 | XRain Auth 的统一身份、XRain 的成员、应用准入和授权 | 复用身份与授权机制；业务仍要明确岗位职责、落实允许的范围并验证实际操作 |
| 保存、查询和维护业务资料 | XRain 对象描述、记录读写、字段授权、视图和文件操作 | 不重建通用 CRUD、审计和导入框架；业务模型、资料含义、适用关系与采用条件仍由业务负责 |
| 页面、顾客接待和应用承载 | Workforce 公共顾客组件、宿主、导航和公开 SDK | 复用公共入口；目标业务的接待、选车和后续衔接仍需有自己的结果责任 |
| 对话与智能体 | Workforce 消息与对话界面、Runtime 定义、会话和工具执行 | 不重建通用运行引擎；业务指令、工具、真实沟通效果仍须交付 |
| 普通函数与版本管理 | XRain 的函数编写、源码、版本、测试、应用选用界面及调用能力 | 复用函数管理；业务负责当前计算口径、函数内容和独立核对。只有真实业务要求且平台不能满足时才补专用管理能力 |
| 跟进与定时提醒 | Workforce 的任务、计划与受支持的触发方式 | 复用通用机制，交付客户、约定和实际提醒的业务衔接；不能仅凭存在任务表就宣布自动提醒可用 |
| ERP、CRM 等已有系统中的事实 | 原系统的维护职责、可用接口、授权和使用范围 | 原系统继续持有的事实可直接接入；只有确有新业务事实时才新增模型，避免重复维护 |

按命中能力读取 [产品知识与责任项目](https://github.com/xingshukeji/skills-hub/blob/main/skills/shzw-workforce-business-development/references/knowledge-ownership.md)中的相关专题。模型与平台基础参考[对象自带能力](https://github.com/xingshukeji/skills-hub/blob/main/skills/shzw-workforce-business-development/references/object-foundation.md)，业务过程参考[业务主线](https://github.com/xingshukeji/skills-hub/blob/main/skills/shzw-workforce-business-development/references/business-mainlines.md)。这些链接用于按需取得知识，不要求启动另一整套开发方法或预读全部专题。

已取得对应团队技能时，可按加载结果的实际资源目录读取上述文件。不得从本技能的安装路径推断其他仓库的位置；真实源码路径通过项目入口或已保存项目定位。

第一次核对后，形成业务项目仍须承担的结果范围。例如铵帮需要按本期目标承担两品牌业务资料、模型、销售测算、报价与跟进、特价材料和智能体效果。这里不能据此宣布这些内容尚未开发，下一次核对才判断本期可采用哪些成果。

## 第二次：将目标项目实际进展对照任务

读取目标项目的模型、装配、业务实现、相关测试和使用证据，将其对应的需求与本期目标对照。铵帮自己的算法、特价、成交和报表属于这一层。先判断适用与采用，再判断差距；已明确重做的范围不必先跑完旧系统来决定是否保留开发任务。

| 核对方向 | 要回答的问题 | 对当前任务的影响 |
| --- | --- | --- |
| 当前任务 → 目标项目成果 | 同名业务是否存在？是否符合本期需求且被采用？还有什么差距？ | 仅保留适用且被采用的部分；按真实差距安排重做、补齐、配置或核实 |
| 目标项目重要成果 → 当前任务 | 已有或在办功能是否在本期范围？属于采用、重做、排除还是待确认？ | 识别遗漏、旧范围和重复分配；不把每个源码模块都转成任务 |
| 业务过程 → 产品与任务衔接 | 下游真正能用到上游成果吗？ | 定位入口、业务规则或采用条件的缺口，不能用组件分别存在证明完整可用 |

功能树也是待核对材料。原始需求明确不做系统内审批时，旧原型中出现审批页面不能成为保留审批开发的理由。需求、页面或任务变化后，检查受影响范围；不能用旧功能树与新任务的关联完整性证明当前目标已覆盖。

## 为“已经有”保留准确的证据范围

沿当前业务的真实使用过程核对必要事实：

1. **目标适用与采用**：证据对应的需求仍有效吗？用户是否已决定替换或重做？旧原型被验证成功，不能证明它被新目标采用。
2. **能力提供**：产品是否支持所需行为，当前接口、类型或实现是什么。需求文档、菜单名称和旧任务“完成”状态不单独证明能力存在。
3. **应用消费**：业务入口是否使用了这项能力，业务对象与角色是否适配。公共组件可用不等于具体业务已经接入。
4. **目标准备**：相关版本、资源、配置、资料和授权是否在指定环境具备。本机源码或其他租户的结果不能证明当前目标已就绪。
5. **实际使用**：原业务身份能否从入口完成需要的动作，结果能否保存回读并供下一环节使用。保留操作覆盖的品牌、角色、版本与环境，不扩大结论。

复用仍适用的可靠证据；只有事实变化或证据不足时补查。包已发布、源码已更新和目标进程已采用不能互换。旧测试通过只能说明对应旧行为，不给新口径背书；新计算应使用独立业务预期核对。只读权限或资料不足时，写清尚未核实的范围，继续不依赖该结论的拆分。

## 将差距转成适当的工作

以下是工作性质的判断，不是要求任务表新增同名进度状态，也不要求每项功能拆成多行。

| 当前事实 | 任务处理 |
| --- | --- |
| 已满足当前目标、被本期采用且有适用证据 | 无需重复开发。作为输入；有明确交付核验要求时只核对对应范围 |
| 平台能力适用，目标缺模型配置、资料、授权或连接 | 配置接入。说明所需业务结果；若还需业务代码，明确开发部分，不把它藏在“配置”里 |
| 旧原型或验证实现已被新目标替代，或用户明确重做 | 设计与开发重做。旧成果提供经验，不能抵扣当前工作；后续验证针对新目标与新结果 |
| 本期采用的实现符合目标、无已知功能改动，仅缺使用证据 | 仅验证。限定品牌、角色、版本与场景，发现差异后交对应责任方修正 |
| 部分成果适用且被采用，另有明确缺项 | 业务增量或修复。保留有效部分，交付缺少的结果；不将整项压成测试，也不一律重写 |
| 当前目标确需能力，平台与项目均不能满足 | 必要的新开发。说明业务差异与责任方；不能因为平台不支持就删掉需求 |
| 本期明确排除，或仍由外部业务流程承担 | 本期不建设对应系统功能；需要的材料与结果衔接仍列入业务范围，不能连同用户目标一起删掉 |
| 是否适用、是否采用或需求含义尚未明确 | 定向确认会改变分工的事实，只保留受影响的未决范围；草案不直接成为开发约束 |

保留完整业务目标与本次工作范围的对应关系。拆分中的“已具备”来自证据；“暂不做”来自授权范围或已确认优先级，两者不能互换。不要把“当前产品不支持”解释成“需求不需要”。

任务可以保留稳定的业务名称，在范围里说明当前是核实、配置、补齐或修复。只在存在不同责任方、独立交接结果或明确风险时拆开这些工作；不要求为每项功能生成“调查—设计—开发—测试”四行。

## 让依赖指向真正缺少的结果

已确认且仍适用的模型是输入，不必再创建一个“全量数据建模完成”的等待条件。重做中的模型按已确认部分逐步提供输入，不能让全部业务等待整张图定稿。公共能力缺陷由其责任项目维护，业务任务写明等待哪个修复结果、哪些范围仍可推进；拆分不授权修改平台、发布或部署。

同一产品的通用能力只由一个责任方补齐，各业务按各自差异接入。业务总负责人继续核实实际消费与整体结果；平台修复完成或包已发布，不能代替业务环境已采用并可用。

在当前任务说明或简短对照中表达“当前目标—适用的产品输入—项目成果采用判断—剩余结果与依赖”。最终仍回到面向人的任务、专业判断与协作。不要为一次拆分新建永久功能登记系统、复制产品契约或保存另一份随时过期的全量能力清单。
