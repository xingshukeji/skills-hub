# 任务拆分的好坏示例

这些案例来自销售助手任务拆分及 2026-10-27 的纠正。案例保留判断失误、事实前提和反例，不维护产品的实时完成状态。使用时先核对当前需求、成果是否适用及是否被采用，不复制任务名称或结论。

## 按问题选择案例

| 遇到的问题 | 案例 |
| --- | --- |
| 把数据建模写成建表指令，或把评审稿当定案 | 一 |
| 业务重做与公共能力复用混为一谈 | 二 |
| 旧权限能用，就把新业务权限全部改成测试 | 三 |
| 平台已有文件能力，却重复开发或漏掉新资料工作 | 四 |
| 旧实现测试通过，就判断本期只需测试 | 五 |
| 业务先后顺序变成研发等待 | 六 |
| 持续职责、虚拟负责人或均分行数代替结果分工 | 七 |
| 任务直接变成长智能体提示词 | 八 |
| 全新建账被误解为全部归零或必须保留旧业务 | 九 |
| 业务内没有按钮，就新增平台已有的管理系统 | 十 |
| 旧功能树与任务互相印证，遗漏新需求或保留排除项 | 十一 |

## 一、数据建模：说明用途，把结构留给负责人

**事实前提。** 两品牌原始资料与销售过程正在重新梳理，新的 E-R 图仍待评审。用户已经确认本期不做车辆返利；平台提供记录身份、审计与读写能力。

**差例。** “按这张图建立十五张表和以下关系，逐项完成 CRUD。”它把候选结构当成定案，也把平台已有机制混进建模工作。另一个差例只有“完成数据建模”，没有用途和判断依据。

**好例。** “任务：数据建模。根据新整理的两品牌资料和销售过程，形成能解释业务事实、适用关系及必要历史的模型，供资料维护和销售测算使用。由负责人提出结构、说明设计判断和未决问题，并推动对应范围评审。”已确认排除返利作为业务范围；图中的对象数量不作为任务验收条件。

**为什么好。** 人承担专业判断与可交接结果。已经确认的业务决定与尚在讨论的结构分开，旧验证模型也不会自动成为新设计约束。

**边界。** 如果某段模型仍适用且已决定沿用，应作为输入。只有受未决定义影响的工作需要等待，不能让所有开发等整张图定稿。

## 二、顾客接待：业务要重做，公共机制仍复用

**事实前提。** Workforce 提供公共顾客接待与会话能力。铵帮旧接待、选车和测算入口属于验证，用户要求按新目标重做业务 UI 与实现。

**差例。** “已有接待页，所以只测一下接待流程。”相反的差例是“全部重做顾客系统、聊天窗口和会话引擎”。二者分别忽略了新目标与公共产品。

**好例。** “任务：顾客接待与选车。围绕新销售过程重新形成接待与选车体验，复用公共顾客和对话能力，使销售能表达需求、了解车型配置并进入适用方案。负责人根据原始场景决定交互，核实与测算和跟进的衔接。”

**为什么好。** 业务责任完整，公共机制不重复分配；旧页面不再限制负责人设计。

**边界。** 旧功能树曾要求未登记顾客直接试算，不能据此证明新需求也要求这一点。先核对新接待范围；确认后再决定所需衔接，不能把观察到的旧页面差异自动变成开发任务。

## 三、人员权限：已有身份不等于新对象已经配置好

**事实前提。** 统一身份、成员、应用准入和授权机制已有。新业务模型与职责正在调整：销售使用本人记录，店总查看本门店业务及获准的谈价依据。

**差例。** “开发销售登录与权限系统。”另一个差例是“旧销售账号能登录，权限工作仅做测试”；也不能为方便核验直接给管理员权限。

**好例。** “任务：业务权限配置。使用既有身份与授权能力，按新模型和已确认职责落实销售、店总与维护者的业务范围，使允许与拒绝的操作有明确依据并可供验收。”

**为什么好。** 当前有实际配置工作。平台存在与本期配置完成分别判断；权限测试仍需针对新的业务动作。

**边界。** 若本期对象、职责与配置均未变且已有适用证据，剩余可以只做有范围的验证。出现平台不支持的真实授权语义时，交平台责任方处理；任务拆分不额外授权改账号或权限。

## 四、资料导入：复用文件能力，重新交付业务输入

**事实前提。** XRain 已有记录文件操作与批量接口。铵帮曾验证长春部分资料导入，但当前两品牌模型、资料关联及采用范围变化；产品政策关系已在线下整理。

**差例。** “为两个品牌分别开发 Excel 解析器、导入引擎和导出框架。”另一种差例是“之前导入成功，新资料工作完成”。

**好例。** “任务：业务资料准备与导入。核对本期两品牌资料的含义、单位、引用及未明确条件，按对应已确认模型，通过平台文件能力形成可查可核对的业务输入。业务资料管理另行承担维护体验与新业务规则。”

**为什么好。** 平台机制复用，资料准备、模型映射和业务使用仍有责任人。旧导入证据不能自动覆盖新对象和新资料。

**边界。** 已知平台恢复缺陷交其所有者修复，业务只等待受影响批次的必要结果。资料核对仍能先做；不能把全量线下匹配再搬成线上规则引擎，除非新需求确实要求。

## 五、销售测算：同一份代码，采用决定不同，任务就不同

**事实前提。** 铵帮曾有两品牌算法、预算求解、特价、成交和报表实现，定向测试通过。用户明确这些只是验证，UI 与实现要按新目标大改；新资料已简化计算与产品政策关系，本期取消车辆返利。

**差例。** “算法和测试已经有了，销售计算只剩正确性验证。”这是本次实际误判：把代码存在当成新目标采用，把旧测试当成当前交付基础。

**好例。** “任务：销售测算。按新资料与确认口径重新交付当次销售测算，复用平台普通函数及已整理的关联，使结果可解释、可核对并供报价与比较使用。负责人判断计算组织方式。”另以“测算业务核对”取得新口径下的独立预期与业务结论；是否分开取决于独立责任和交接需要。

**为什么好。** 用户已确定重做，开发责任不能被测试替代。公共函数管理仍可复用；旧测试用于理解旧行为，不能证明新测算正确，也不必把旧测试重新跑过作为重做前提。

**反例条件。** 如果另一项目的现有测算符合当前需求、已经决定采用、没有已知功能改动，只缺指定品牌和角色的真实使用证据，则剩余可以是“计算正确性验证”。若仅有一处已知公式差异，则安排该差异的修改与对应验证。不能把“发现代码”固定映射成测试，也不能把“尚未验证”固定映射成重写。

## 六、依赖：需要什么成果，何时需要

**事实前提。** 新测算、报价展示和谈价记录由不同人员协作。真实比较需要测算结果，历史需要明确每轮条件；交互设计和业务含义可以先约定。

**差例。** “报价展示必须等销售测算整项完成；销售测算必须等报价页面完成。”或为了消除循环任意删掉一条边；或把全部业务都挂在“数据建模完成”之后。

**好例。** “报价展示与方案比较先按销售判断需要开展设计，与销售测算共同明确结果含义；真实展示和比较消费对应测算结果。谈价记录使用已确认的模型范围，与二者约定应保留的业务依据，不等待所有页面完成才开始。”

**为什么好。** 每个关联都能说明具体阻塞什么、目前能先做什么。业务运行顺序不自动成为整项研发前置条件。

**边界。** 本期特价在公司现有流程外部处理：材料生成开发不等待系统内审批任务，后续按批准条件继续业务才需要真实外部结果。联调也只消费实际纳入的成果，不能先挂全部任务再用“可以分批”补救。

## 七、分工：有限结果比行数与岗位名更重要

**事实前提。** 项目统筹和日常环境支持长期持续。两位开发者已有业务分工，建模与业务确认的具体责任人尚未落实。

**差例。** “项目统筹，负责人：项目负责人，验收：持续协调。”或为了各有五项，把完整业务拆成数行；又或把未知责任填成虚构岗位，宣布全部已分配。

**好例。** “持续统筹写入协作安排；有明确交付时列有限任务，例如团队能使用本批新成果的联调版本。已知人员按业务结果负责；其余负责人保持空缺，写清需要落实的结果责任。”

**为什么好。** 任务有可判断的完成点，未知责任没有被藏住。分工按进展调整，不追求行数均衡。

**边界。** 用户要求容量评估或已有具体交付风险时应评估工作量，但不能用任务条数代替实际复杂度。

## 八、使用智能体：任务要求人作判断

**事实前提。** 销售要看懂方案费用、条件和差异。负责人可使用智能体；尚无业务理由预定布局、组件或内部步骤。

**差例。** “复制以下提示词：创建三个页面、调用指定接口、依次提交文件，完成即验收。”把同样步骤塞进验收标准也没有解决问题。

**好例。** “任务：报价展示与方案比较。依据原始销售场景和本期测算口径，使销售能够理解不同方案的支出与适用条件，并向顾客解释。负责人决定表达与实现方式，用业务依据核实结果。”

**为什么好。** 人必须理解业务判断、选择方案并负责结果；怎样使用智能体属于执行方法。任务不替人设计，也不只留下‘完善报价能力’的空话。

**边界。** 已确认的精度、品牌规则和范围仍要保留。主动性不等于没有约束，也不要求通过手工作业证明思考。

## 九、全新建账：分别判断管理重建与业务重做

**事实前提。** 用户要求取消旧编号、清空日期、按全新的任务管理。随后又明确铵帮原有业务 UI 与实现只是验证，要求按新目标重做。

**差例。** “承接旧任务 A、B，原记录保留历史反馈。”另一种差例套用“清理管理记录不代表重做产品”，据此继续把旧验证成果当本期基础；相反地，把统一身份和平台导入也清零同样错误。

**好例。** “当前任务只说明本期目标、适用输入、结果、责任与依赖。旧验证业务按重做处理，基础产品按适用范围复用；日期按授权留空。旧迁移编号和过程说明不出现在任务正文。”

**为什么好。** 管理方式与业务采用分别依据用户要求，不用一句通用原则覆盖具体纠正。

**边界。** 用户仅要求重新建账、并未否定已采用成果时，仍保留有效成果。状态描述本次任务的进展：‘待开始’可能是新一轮重做或验证，不能单凭状态断言从来没有代码。

## 十、函数管理：先找平台正式入口，再判断要不要开发

**事实前提。** XRain 具备普通函数编写、版本、测试和应用选用的界面与接口。新目标使用普通线上函数；铵帮旧原型中的独立算法采用体系不再作为本期要求。

**差例。** “铵帮的函数详情只支持查看版本，缺少采用按钮，需要开发计算规则管理台。”这曾把一个业务页面的观察扩大为全平台缺能力，也保留了已被新方向替代的管理体系。

**好例。** “不单列业务算法管理台开发。销售测算交付新业务函数；联调配置与版本交付使用平台已有管理入口落实实际版本；业务核对验证实际执行与新口径一致，必要历史依据能够解释。”

**为什么好。** 对照的是维护者实际要完成的事与平台受支持路径，既省去重复开发，也保留配置和真实采用的责任。

**边界。** 如果真实使用角色不能使用平台入口，或新业务确需额外审批、隔离或交互而平台确实不满足，应交代具体差异再安排业务能力。本案例不能成为永久禁止专用管理界面的规则。

## 十一、覆盖审查：旧表不是需求的证明

**事实前提。** 旧功能树包含审批界面和算法管理；新原始流程明确一期不做系统内特价审批，只生成材料并补录外部结果。新梳理还涉及通用上装、谈价轮次和店总查看谈价依据。另有独立在办的微信小程序工作。

**差例。** “每项任务都关联功能树，所以范围完整。”或看到小程序源码就立即加入本表；或把新 E-R 评审稿全部对象转成开发约束。

**好例。** “从新原始需求检查接待到管理的业务过程，再对照平台输入、本期采用成果和任务责任。移除系统内审批开发，保留特价材料与外部结果；让谈价跟进与门店管理有归属。旧功能树和项目说明同步按业务目标修正。小程序按已确认的独立范围处理，不重复扩大本表。”

**为什么好。** 正向查需求是否覆盖，反向查实际工作是否有归属，同时排除过时功能。新的业务清单表达用户结果，不重新规定旧页面布局。

**边界。** 已确认的业务事实立即用于拆分；评审中的结构和其他未决范围继续标明。关联完整、数量匹配和没有依赖环都只是结构检查，不能单独证明业务正确或全部需求已定案。
