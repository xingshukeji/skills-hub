# 任务拆分的好坏示例

以下是虚构的工作场景，用于比较判断方法，不代表某个客户的模型、业务规则或当前进度。使用时先核对实际需求、产品能力和本期采用决定。

## 按问题选择案例

| 遇到的问题 | 案例 |
| --- | --- |
| 把待评审模型当定案，或把专业任务写成建表指令 | 一 |
| 业务重做与公共能力复用混为一谈 | 二 |
| 已有身份不等于新业务权限已配置 | 三 |
| 平台已有文件能力，却重复开发或遗漏资料工作 | 四 |
| 旧实现通过测试，就判断本期只需测试 | 五 |
| 业务使用顺序变成研发整体等待 | 六 |
| 长期职责、虚拟负责人或均分行数代替结果分工 | 七 |
| 任务直接变成长智能体提示词 | 八 |
| 重新建账被误解为业务全部归零 | 九 |
| 应用内缺按钮，就新增平台已有的管理系统 | 十 |
| 旧功能树与任务互相印证，遗漏新需求或保留排除项 | 十一 |

## 一、数据建模

**前提。** 图书借阅的业务资料正在整理，新关系图仍待评审。平台已有记录身份与读写能力。

**差例。** “按评审图建立八张表和所有关系，完成 CRUD。”另一个差例只有“完成数据建模”，没有用途和判断依据。

**好例。** “根据借阅过程和已确认资料，形成能解释业务事实及必要历史的模型，供藏书维护与借阅记录使用。负责人说明结构选择和未决问题。”

**理由与边界。** 人承担结构判断；待评审图不能变成固定验收。已确认且仍适用的部分可以先提供，不让所有工作等待整张图。

## 二、重做业务，复用公共机制

**前提。** 某项目的旧课程报名页面是验证原型，用户要求按新目标重做。平台已有记录、身份与公共界面机制。

**差例。** “旧页面能打开，本期只测试。”另一个差例是“重写平台身份和记录系统”。

**好例。** “重新交付课程报名体验，使用平台已有机制，并核对报名、取消和查询的衔接。”

**理由与边界。** 新业务仍需交付，通用机制不重复建设；实际不适配的公共能力要说明具体差异。

## 三、身份与业务权限

**前提。** 统一身份和授权机制已有；新业务职责已确认，目标对象权限尚未配置。

**差例。** “开发新的登录系统。”或“旧账号能登录，所以本期权限只需测试。”

**好例。** “复用既有身份，按本期职责配置对象与记录范围，并验证允许和拒绝的业务动作。”

**理由与边界。** 平台提供机制与项目已完成配置是两件事。若职责、配置和使用证据均未变化，剩余工作可以只验证。

## 四、业务资料导入

**前提。** 平台提供文件和批量记录能力。目标项目的旧资料已导入，新资料和采用范围发生变化。

**差例。** “为每份资料开发独立导入引擎。”或“旧资料导入过，新资料无需处理。”

**好例。** “核对新资料含义与引用，按已确认模型使用平台能力完成导入，并交付业务可维护的结果。”

**理由与边界。** 通用机制可复用，资料准备和业务衔接仍需负责。已知平台缺陷交其所有者；不受影响的资料核对可以先做。

## 五、旧实现与本期采用

**前提。** 旧排班原型及其测试曾通过；用户已决定按新规则重做，平台的函数管理仍适用。

**差例。** “代码和测试已有，本期只验证。”

**好例。** “按本期规则重新交付排班计算，复用平台函数管理，并按新业务依据核对结果。”

**理由与边界。** 测试通过只证明旧行为。若另一项目的实现仍符合目标、已被采用且没有已知改动，而仅缺实际使用证据，剩余可以是限定范围的验证。

## 六、依赖与时点

**前提。** 页面展示和计算由不同人员负责，真实展示需要计算结果，交互设计可以先使用约定样例。

**差例。** “页面整项必须等计算整项完成；计算又必须等页面完成。”

**好例。** “双方先约定结果含义，页面可用样例设计；真实联调前取得对应计算结果。”

**理由与边界。** 写明缺少什么、何时需要和可以先做什么。业务运行有先后，不自动意味着研发整项串行。

## 七、结果与分工

**前提。** 统筹和环境支持持续发生；两位成员负责不同业务，部分负责人尚未落实。

**差例。** “持续协调，负责人：项目负责人，验收：继续协调。”或为了平均分配把一个结果拆成多行。

**好例。** “交付团队可使用的联调版本；已知人员承担相应业务结果，未落实的负责人保持待定。”

**理由与边界。** 有限成果能判断完成；任务行数不代表工作量。用户要求容量评估或已有具体风险时，应另行评估。

## 八、人的专业判断

**前提。** 负责人需要让使用者理解方案及条件，可以自行选择是否使用智能体。

**差例。** “复制提示词，依次创建三个页面和四个接口，执行完即验收。”

**好例。** “交付使用者能理解、比较并解释的方案结果；负责人依据业务资料决定表达和实现。”

**理由与边界。** 人保留方案判断与结果责任；已确认的业务约束仍然有效，不要求通过手工操作证明思考。

## 九、重新建账

**前提。** 用户授权重新整理任务记录；部分旧业务仍被采用，另有旧原型已明确重做。

**差例。** “新任务表意味着所有产品能力归零。”或“重建管理记录后必须继续采用所有旧原型。”

**好例。** “任务正文写本期目标、适用输入、责任和依赖；沿用已采用成果，对明确重做的范围保留开发责任。”

**理由与边界。** 管理记录与业务采用分别判断。只有明确授权才删除历史、清空日期或重置状态。

## 十、平台管理入口

**前提。** 平台已有函数编写、版本和应用选用入口；某业务页面没有管理按钮。

**差例。** “业务页面没有按钮，必须新建一套函数管理系统。”

**好例。** “先核对实际维护角色能否使用平台入口，再安排函数内容、选用配置和结果验证。”

**理由与边界。** 应用页面的缺口不等于平台缺能力。若角色确实无法使用，或业务有平台未覆盖的真实需求，再安排对应差异。

## 十一、需求覆盖

**前提。** 新需求要求接入原有资料，并明确本期不建设移动应用；旧功能树包含移动端开发，另有不属于本期的独立工作。

**差例。** “每项任务都关联旧功能树，所以需求完整。”或仅因发现其他源码就把它加入本期。

**好例。** “从新需求检查业务结果，再对照平台输入、项目采用和任务责任；移除被排除的移动端开发，保留原有资料的接入。”

**理由与边界。** 正向检查需求覆盖，反向检查任务依据。关联数量和无依赖环只能证明部分结构，不能证明业务正确。
