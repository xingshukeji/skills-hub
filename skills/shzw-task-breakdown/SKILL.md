# 面向业务结果的任务拆分

任务表帮助人承担结果、理解相互需要的成果，并根据进展调整工作。负责人需要自行理解原始需求、作出专业判断、设计做法和内部步骤，并决定如何使用智能体。任务数量少、文字短或分配平均，都不能单独证明拆分合理。

## 从需求到任务草稿

需求跨多个来源、任务较多或旧成果有争议时，按以下顺序工作。记录随本次草稿保存，不另建长期台账。简单的一项调整直接核对相关依据和结果。

1. **提取目标。**从原始需求和已确认决定列出业务结果、排除项及未决范围，保留简短的来源对应；不要用现有任务表代替需求。
2. **核对基础。**逐项查基础产品能力，再查目标项目成果是否适用、已被本期采用和已有使用证据；注明依据及仍需承担的差距。
3. **保存并核对草稿。**按人的责任和可交接结果，在本次工作记录中先保存待调整草稿。将提取的每项业务结果对照到任务、责任及依赖，再反查旧任务和项目成果是否过时、遗漏或超出范围；按发现修订草稿。只读审查以原任务为被审对象，不另造草稿。
4. **调整并回读。**草稿核对后，按已有授权写入任务。回读受影响任务、责任和依赖，核对修订是否落实；只读审查报告发现，未能确认的部分如实保留。

## 确定这次要交付什么

沿用当前请求及必要前文中的目标、排除项和已确认选择。区分审查现有任务、提出新拆分、执行已授权调整；只读审查不修改任务系统。已有调整授权覆盖同一目标时继续，不因发现内部步骤重复确认。

读取当前任务及相关原始需求。仓库资料通过目标项目入口定位；外部任务表使用用户指定的身份和工具。把用户意图、业务规则、已有实现和未决问题分开判断，不用旧任务清单证明需求完整。

先核对需求版本和采用范围。用户已确认的重做、排除项和范围变化优先于旧原型、旧实现及测试；正在评审的模型或方案只在已确认部分约束任务。新版资料与旧文档冲突时，指出具体影响，只暂停尚不能判断的部分。不能把“已有实现”“适合新需求”“本期决定采用”“目标已经验证可用”合并成一个结论。

需求依据可以只写可识别的文件名。没有链接不妨碍引用；没有读到原文时，不得声称已核实内容，也不得编造文件名。只暂停依赖缺失事实的判断，其余范围继续。旧工时估计不能代替现行目标。

## 分别核对基础产品与目标项目

先确定要交付的项目，再按[产品与项目核对方法](references/product-baseline.md)查影响拆分的事实。第一次只查 XRain、Workforce、Runtime、统一认证等基础产品。确认通用能力可以复用到哪一步，以及目标项目仍须承担哪些业务结果。核对公共接口、维护界面与受支持的使用方式，不因业务应用中缺少某个按钮就断言平台没有能力。

第二次单独查目标项目自身已做的工作。先判断原型、模型、实现与测试对应什么需求，是否仍适用，以及本期是否采用，再核对尚缺的结果。项目自己的实现不能证明基础产品已替它完成业务。用户明确原有 UI 和业务实现只是验证、本期需要重做时，它们只提供经验与风险线索，不能抵扣本期开发，也不必先重复运行旧测试来决定是否重做。

两个方向都要看：从任务找现有成果，防止重做；从目标项目的重要已有或在办成果找任务归属，防止漏项和旧任务表脱离实际。新功能没有对应任务时，先核对是否属于本表交付范围，不能仅因源码存在就扩大范围。不要只在每项任务中加一句“结合现有能力”而不查实际差距。

明确哪些需要设计或开发、哪些只需配置接入、哪些仅需验证、哪些无需重复建设、哪些本期不做、哪些尚待确认。平台提供、业务已接入、目标环境已具备和原用户实际可用是不同事实。源码、测试、安装记录和实际操作各有证明范围；一个角色或使用范围可用不能代表全部业务已交付。

只有现有成果符合当前目标、已被本期采用且没有已知功能改动时，才可将剩余工作判断为“仅验证”。目标变化、已知缺项或用户明确重做时，应保留相应开发责任与后续验证。事实不明时定向核实，不把“不知道有”写成“没有”，也不把“没有验证”自动写成“需要重做”。

用核对结果确定当前任务尚需取得的结果；完整目标继续由原始需求承载。适用且被采用的成果作为输入；配置或接入能满足需求时不新增基础机制开发。业务重做不自动扩大为公共平台重做。只检查影响拆分的范围，复用仍有效的证据；拆分不要求顺带完成整套系统验收。

任务名称可以稳定，例如“数据建模”；范围则交代具体已有基础和本次差距。将平台缺陷与业务缺项交给各自责任方，业务结果仍保留一个总负责人。不强制另建全产品台账或状态列，也不因已有代码就自动把整项任务标为完成。

## 用对照示例校准判断

新建拆分或审查质量时，读取[好坏示例](references/examples.md)中与当前问题相关的案例。每例包括事实前提、差例、好例、判断理由及适用边界。比较“任务要求人作什么判断、使用什么已有能力、还缺什么结果”，不要只模仿好例的句式。

本次核实得到的新差异优先于示例前提。案例不是固定功能清单、现行完成状态或产品契约；不能因案例中曾有某项缺口，就为当前项目自动新增同名任务。

## 选择有意义的任务边界

先明确谁要解决什么问题、希望取得什么结果，再判断哪些结果值得单独交给人负责。业务能力和数据建模等专业工作都可以成为任务；不强制统一按页面、表、接口、技术层或开发阶段切分。

- **拆开**：存在不同的责任主体、可独立交接的成果，或需要独立判断的关键风险。拆开后的每项都应有自己的用途与完成依据。
- **合并**：几项只有内部执行步骤的差别，始终共同变化，且分别完成没有使用价值。不要因负责人相同就合并不同结果，也不要为减少行数制造包罗万象的大任务。
- **保留整体责任**：跨人的业务流程仍有明确的整体结果责任。分工不应让所有人只对自己的组件负责，最后无人对实际可用负责；角色名称不能冒充已落实的负责人。
- **区分持续职责**：统筹、答疑、日常环境支持通常属于协作安排。只有产生一个有限的交付结果时才列成任务，避免长期停在“进行中”充当进度。

不设固定任务数、统一粒度、工时比例或平均分配目标。人员安排按已知能力、责任和实际进展确定；只有用户要求容量评估或存在具体交付风险时才分析工作量。

## 写清结果，保留专业判断

使用读者认识的业务或专业名称，例如“数据建模”“销售测算”。不要给所有任务套上“能力交付”等泛化后缀，也不要用陌生编号表达任务之间的关系。

每项提供足够的上下文，让负责人回答：为什么做、依据是什么、已有基础是什么、还缺哪些由我负责的结果、谁需要这些结果、怎样判断已经满足需求。通常用简短的目标与范围、需求依据、预期结果、负责人及必要依赖即可。适配现有工具，不为套模板增加全部字段或重复填写同一内容。

预期结果要能从业务或专业使用中观察。例如“销售能解释方案费用与适用条件并作出比较”，比“完成报价能力”更能判断价值。只保留影响判断的完成依据，不把表结构、函数、页面布局和逐步操作换个名字塞进验收条件。

保持以下边界：

- 原始需求和已经确认的业务约束仍然有效。保留人的主动性不等于放弃范围、责任或结果验证。
- 专业方案由负责人形成。数据建模任务说明要支持的业务事实与使用目标，只将仍适用且已确认的模型作为约束；不在任务中预先指定要建哪些表，也不把评审稿的对象数量变成验收要求。明确要求遵守的兼容或监管约束应注明来源，不能作为可自由忽略的建议。
- 负责人可以提出需求缺项、冲突和改进建议，并说明影响；不能自行把未经确认的业务选择当成既定要求。
- 智能体是负责人可选择的执行工具。任务表不预制可直接转交智能体的长提示词或操作脚本，也不强制手工执行来证明思考。人的责任体现在需求判断、方案取舍和结果核实。
- 负责人未知时如实标明尚未落实，并说明受影响的结果。不要虚构人员、制造新岗位，或用“某某负责人”使分工看似已经完成。

## 说明真正需要的依赖

对每条关系说明：从哪项工作取得什么成果，在什么动作或判断之前需要，以及目前能先做什么。依赖使用任务名称；系统内部 ID 仅用于定位记录。

区分三种情况，并用简短文字表达；不必为此新建关系系统：

| 关系 | 对推进的实际影响 |
| --- | --- |
| 开展某部分工作所需的输入 | 缺少它时，仅阻塞需要该输入的部分 |
| 联调或形成完成结论所需的成果 | 方案设计、样例研究等可提前开展，最终结论需对应成果 |
| 并行协作与约定 | 双方共同澄清交接内容，不表示一方整项完成后另一方才能开始 |

审查依赖时检查：

- **必要性**：去掉这项输入，具体哪个动作或结论无法成立？只因同属项目、需要沟通或将来会集成，不足以成为整项前置条件。
- **已有输入**：仍适用的资料、已确认模型和现成服务不因重新整理任务而失效；已被新目标替代的旧成果不能继续充当前置基础。仅把尚缺的结果形成待完成依赖。
- **层次一致**：按子范围消费的成果不得表达为整项完成后开工。表格若无法表达关系类型，直接在依赖说明里写需要的成果和时点，不让关联列暗示错误顺序。
- **方向与闭环**：区分研发成果依赖和业务运行顺序。申请与审批可以共同约定后并行实现；真实申请获得审批决定是业务运行条件。发现循环时定位共同约定或缺少的上游结果，不为消除图上的循环随意删边。
- **实际批次**：联调只关联当前明确纳入的成果。不要把所有可能的成果都挂成前置，再用“可以分批”补救。
- **验证依据**：区分待验证实现、独立业务依据和辅助工具。实现自身的输出不能成为正确性的唯一依据；工具开发也不一定需要等待全部验证完成。

## 整体审查与调整

从一条代表性业务过程检查任务间的衔接。确认完整目标由适用的基础产品、本期采用的项目成果和剩余任务共同覆盖，关键结果不遗漏，边界没有互相覆盖或重复验收；局部完成能被下游实际使用。核对角色、资料、业务动作、智能体效果、验证与交付，不按旧页面逐项复制。功能树和任务表也可能过时，不能用两张表互相印证来代替当前需求与实现事实。

检查说明是否仍替负责人做了方案选择，或反过来只剩“完善、优化、支持业务”等无法判断完成的空话。检查任务表是否要求维护过多状态、关联和重复说明，留下确实帮助当前分工与决策的内容。

审查报告优先给出有证据的问题、影响和调整方向，同时保留经得起检查的安排。不要为展示审查力度强行凑问题，或把建议写成已经落实的事实。

用户要求重新建账时，按现行目标重建活动任务，不在任务正文保留“承接旧编号”、合并过程或预留占位。管理重建本身不代表产品归零；用户同时明确业务重做时，也不能以保留成果为由延续旧设计。删除历史、清空日期和重置状态分别按当前授权处理，不能从一次项目选择推广为默认动作。

## 写入与完成

已获任务系统调整授权时，先核对当前记录和字段，按已审查的边界写入。保留无关业务资料；尊重并发变更。部分写入或响应不明确时，回读已产生的记录再继续，避免重复创建或扩大清理范围。新建任务、发送通知、删除历史及改变权限的外部影响分别核对已有授权。

调整授权范围内的任务及受影响的功能清单、项目说明和视图，避免旧原型仍作为开发依据。写入后回读任务名称、正文、负责人、依赖、状态、日期和相关视图，确认无悬空关联、无错误顺序、无残留旧措辞。数量相等或无环只证明部分结构正确，还需复核依赖含义、业务覆盖与人的判断空间。

完成时报告基础产品可复用范围、目标项目成果的采用判断、需要开发或配置的结果、仅需验证及无需建设的范围，以及实际调整内容。每个重要结论应能对应任务和证据；说明证据适用范围，不用技能示例证明目标已可用。只完成拆分，不代表未决需求已定案、负责人已接受分工或业务实现已经验收。审查任务以有依据的结论完成；调整任务以授权范围实际生效并回读核实完成。
