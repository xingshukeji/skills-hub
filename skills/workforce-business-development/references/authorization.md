# 业务授权设计

## 从职责得到授权方案

把参与者映射到动作、字段和记录范围，用已有授权来源、角色与权限集实现。

例如以下是维修业务的一种设计，不是预置角色：

| 参与者 | 业务动作 | 数据范围与字段 |
| --- | --- | --- |
| 报修人 | 创建申请、查看进展、补充描述 | 本人申请；可读处理结果，不编辑处理结论 |
| 维修人员 | 领取、记录处理过程、完成维修 | 分派给自己的申请；可写处理记录及实际完成数据 |
| 调度人员 | 分派、改派、查看本部门进度 | 本部门业务范围；不因“调度”角色名自动取得全租户权限 |

“本人”“本部门”“指定客户”需要明确对应业务字段和真实身份。平台标准 `ownerId`、业务的负责人 UserRef、创建人和部门字段可以不同；一个名为 `assigneeId__c` 的字段不会自动产生分派或管理权限。

## 几个独立的判断

| 判断 | 实际含义 |
| --- | --- |
| 登录与租户成员 | 用户身份有效，并且属于目标租户；角色名称不建立成员资格 |
| 应用准入 | 该用户能进入这个应用；不自动取得其全部业务数据 |
| 操作能力 | 有权执行对象动作、接口或自定义业务动作 |
| 字段访问 | 当前字段允许读取、创建或编辑；读取还可能脱敏 |
| 记录范围 | Owner、共享规则、人工分享或其他实际支持的范围允许访问这一条记录 |
| 自动化执行 | 实际运行工具、函数或流程的主体拥有对应能力；定义、工具装配和执行资格也要成立 |

按钮可以根据这些结果显示，但服务端仍执行实际授权。平台的角色/权限解决“谁可以操作什么”，企业业务服务解决“这个操作在当前业务状态是否成立”；例如有审批能力仍要核对申请状态与适用业务条件。

## 角色、权限集和权限

全员能力复用 `xrain-all-employees` 自动来源，或包的 `assignmentAudience=allEmployees` 声明与租户绑定，无需逐人分配。接口与生效条件见[初始化基础](initialized-platform.md)。

专项职责用用户承担角色、角色关联权限集、权限集包含权限来表达，也可按目标入口直接给用户绑定普通权限集。有效权限可能来自系统自动来源、包、多个角色或直接关系，撤掉一条绑定不等于权限一定消失。

对象/字段标准权限由有效元数据生成，从实际目录选取后映射到业务动作；不猜权限名。企业专有动作可声明 `custom.*`，由业务处理器检查，声明与页面消费示例见[元数据与前端](metadata-and-ui.md)。

角色按真实职责设置，同一身份通过成员关系和多个角色复用，不因新增职责另建人员。

## 记录范围怎么落地

先确定业务想表达的是所有权、明确分享、按角色共享，还是按当前主体与记录条件共享，再选择平台已有方式。记录条件中的业务关联与权限条件是两件事：页面筛选 `assigneeId__c=本人` 能缩小结果，不构成后端的记录授权。

多个有效范围来源可以共同生效。判断“只看本人”时，既检查本人的正例，也检查其他角色或分享是否扩大了范围。部门层级、User 的直接上级和业务负责关系并不自动等于可读所有下属记录。

需要“只处理本部门申请”时，把主体的组织/角色条件与记录所属部门分别配置。当前共享规则的角色直授与主体条件按 OR 合并；要求两者同时成立时放在主体条件 all 内，不能又添加同角色直授。完整请求示例、租户人员来源、人工分享和 Owner 转移见[组织与记录协作](organization-and-collaboration.md)。业务入口校验不改变用户直接访问记录 API 时已有的权限。

## 跨系统与自动化的执行身份

同一个人可能在 Workforce、XRain 和 ERP 中有不同 ID。当前会话身份决定谁发起操作，实际凭据决定哪个主体访问数据；业务输入中的用户名或负责人不能替代认证。跨系统身份映射要关联来源与租户，沿用已授权的原系统接入，不按任务临时创建新用户。

| 场景 | 权限如何落地 |
| --- | --- |
| 用当前用户访问 XRain | 可信执行绑定或当前会话客户端，平台执行对象、字段和记录授权 |
| 用当前用户访问 ERP | 原系统认可的用户凭据或委托机制；原系统检查其用户范围 |
| 用共享连接器凭据访问远端 | 平台接口权限控制谁能发起；远端按连接器主体授权，个人业务范围由受管操作另行落实 |
| 通过编排发布一个组合操作 | 外层入口按完整业务能力授权；原生记录仍检查执行者的数据权限，内部 raw HTTP 调用按编排规则执行 |
| 记录 After Trigger | 保留事件操作者及上下文；Worker 不自动变为管理员 |
| 普通定时 Routine | 使用配置的实际执行成员；维护 Owner 不等于运行主体 |
| 企业受管后台操作 | 使用已经定义的用途与身份，明确可执行业务及对调用者的检查 |

应用内权限可控制业务能力，Owner、分享等控制记录范围；应用授权不自动补齐原系统权限。遇到拒绝时识别拒绝的是哪个系统和哪个主体，不能用共享管理员凭据掩盖“按用户访问”的失败。具体接法见[系统集成](integration.md)和[自动化](automation.md)。

对外 API Token 固定绑定实际主体和租户，签发者不替代调用者，详见[API 访问](configuration-and-api.md)。智能体还存在订阅与应用选用资格，见[智能体接入](agent-access.md)；获准使用助手不会自动取得其工具访问的业务数据。

## 实现与检查入口

用 `XRainRuntimeClient.applicationAdmission(applicationId)` 读应用准入，`context()` 读当前主体与有效权限；管理写入使用目标交付的合同。

已有 XRain CLI 时，可检查或调整其支持的租户安全资源；下表省略连接参数，使用当前已认证目标。这些命令不等同于应用内角色管理接口。

| 需求 | 命令形式 |
| --- | --- |
| 查看用户授权 | `security user show <用户名>` |
| 查看角色 | `security role show <角色名>` |
| 查看权限集 | `security permission-set show <权限集名>` |
| 将已有角色分配给已有用户 | `security user grant-role <用户名> --roles <角色名>` |
| 将已有权限集关联角色 | `security role grant-permission-set <角色名> --permission-sets <权限集名>` |

使用写入接口时，先区分当前操作是增量变更还是集合替换。集合替换需要读取并合并现有内容，保留其他绑定；遇到修订冲突按新状态重新合并。具体修订字段与撤回要求依据该接口，不将一种管理接口的写法套到另一种接口。

页面和工具按当前主体的 `object.access` 与 Runtime 描述处理字段读写及脱敏，见[元数据与前端](metadata-and-ui.md)。tenantId 和执行 userId 来自可信上下文，不能由浏览器或工具参数指定。

按改动选择实际验证：新增一个可编辑字段就核对该字段的允许与拒绝行为；调整记录范围就比较范围内外的记录；调整工具执行者就核对该执行者。管理员能操作、空列表或隐藏按钮都不能单独证明普通用户的业务权限正确。
