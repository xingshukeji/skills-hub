# 铵帮：一个企业业务落地案例

本例提炼自铵帮业务代码及其使用的发布包，无需访问该仓库。文件名用于说明职责，不是目录规范；代码设计不证明在线环境已全部启用。

铵帮组合原生模型、企业算法与 Workforce。已有 ERP 的项目也可直接接入 API 或采用混合实现，见[平台与业务](platform.md)及[系统集成](integration.md)。

## 业务如何分布

铵帮帮助销售查询车型、解释政策、核算购车方案、处理特价申请并记录业务结果。它将这些内容分布在平台资源、企业服务、页面和智能体工具中：

| 案例中的实现 | 做了什么 | 可以借鉴的地方 |
| --- | --- | --- |
| `business-schema.mjs` | 声明车型、政策、需求、测算、确认、特价申请等对象及字段和关联 | 让模型声明与代码读取字段共享一份业务定义 |
| `application-source.mjs` | 生成 `BizObject`、`BizField`、选项集及 `custom.anbang.*` 权限资源 | 将可安装平台资源从业务模型中生成，保留稳定身份 |
| `runtime-store.mjs` | 使用平台记录 API 查询、保存，通过 `expectedValues` 做条件更新 | 业务可以封装数据语义，同时沿用平台存储与并发能力 |
| `roles.mjs` | 描述销售、运维人员、主管的职责，并把有效权限映射成页面能力 | 业务职责、能力显示与平台实际授权相互对应 |
| `service.mjs`、算法与管理模块 | 车型选择、成本和方案核算、政策适用、申请及业务记录 | 将明确的企业规则落实为可测试的业务实现 |
| `algorithms/artifacts.mjs` | 生成算法源码、输入输出契约及摘要 | 函数产物与模型包分别接入，应用选用版本后才能按该版本执行 |
| `agent-definition.mjs` | 声明业务指令和服务工具 | 让智能体使用真实操作与结果，减少重复实现 |
| 企业 Host、插件与接待页面 | 装入公共宿主、管理页面、业务处理器及公共 `CustomerEntry` | 企业集中开发交互与业务，复用登录、导航、会话和插件生命周期 |

宿主源码与低代码资源包是两部分：前者运行页面和服务，后者提供目标平台中的模型等资源。铵帮本机开发加载当前业务源码，公共能力来自已发布并锁定的依赖包，接入不要求取得公共包或平台的实现源码。

案例的 `application-source.mjs` 生成对象、字段、选项及自定义权限资源，没有把算法作为函数资源一并装入该模型包。算法产物、应用函数关联和所选版本由另外的业务模块与对外接口处理；模型包安装不能代替函数接入。

其 Host/Client 插件通过包入口、`dsh.bundle.patch` 和 profile 装配；Host 的 `apply(ctx, config)` 使用 `ctx.workforceApplications.register` 注册入口、`ctx.workforceHttp.register` 注册处理器，并借 `ctx.effect` 释放注册。这是该企业项目与所消费包的接法。新项目按已发布插件文档及导出类型选择扩展点，不据此假设每种宿主都提供同名上下文服务。

## 已初始化基础如何被复用

铵帮当前消费的 Workforce 0.3.8 发布包包含平台初始化逻辑：先读取目标租户的 `xrain-all-employees`，核对系统归属、有效状态及所需基础权限；专项能力只补已有全员基础以外的权限。旧 `public` 角色和 `default` 权限集仅作兼容观察，不要求业务恢复这条旧关系。这说明“公共权限已有承载位置”直接影响初始化实现，并非只是一条解释性知识。

其消费的基础包括 `queryAst`、记录 get/create/update、最小成员资料和个人设置接口。初始化没有向每位员工再次分配固定集；针对员工智能体管理、定义管理、工作指南或文件调用等特定用途，才复用相应包权限集或补专项权限。包资源有效性、实际用户职责和业务记录范围仍独立检查。

同一逻辑将 `workforce__task__c`、`workforce__chatChannel__c` 等作为已安装公共包的资源处理，不由销售模型再造一套。`workforceWorkGuide__c` 是按需要维护的 User 扩展字段，不应被误写成所有 XRain 新租户都必有的内置字段。这些是发布包中的实现证据，不代表任意铵帮在线环境已执行所有配置。

智能体据此完成新需求时，应直接复用已有通用授权、人员和协作模型，再增补企业自己的能力。单租户公共权限、应用包全员贡献、稳定 User 引用及默认字典的具体写法见[平台初始化基础](initialized-platform.md)；消费此 skill 无需读取案例包内部文件。

## 建模例子：测算、确认与历史

一份测算记录关联车型、需求修订、采用依据和函数版本；一次确认有自己的记录，关联被确认的方案。这样既可以解释“当时怎么算的”，又能读取“后来是否确认”。当前价格或政策改变时，可以生成新的测算并保留原结果。

这体现的是按业务事实区分对象：计算结果、用户确认、实际成交是不同事实。其他业务是否需要这些对象，要看其过程与追溯需求，简单表单不必复制整套历史模型。

铵帮同时保存结构化字段和业务内容快照：字段用于查询、关联与界面，快照用于保存当时完整的计算依据。生成字段与读取快照时有一致性处理。这个选择适合其历史核算需求；普通业务可直接使用平台字段，没有必要普遍增加 `content__c`、签名或双份内容。

## 权限例子：三种实际业务职责

| 铵帮角色 | 案例中的能力 |
| --- | --- |
| 销售 | 价格测算、顾客接待、本人特价申请及本人提供/成交记录 |
| 运维人员 | 资料和政策维护、测算核对；使用 `custom.anbang.catalog.manage`、`custom.anbang.policy.manage`、`custom.anbang.quote.review` |
| 主管 | 特价审批、测算核对和报表；使用 `custom.anbang.price.approve`、`custom.anbang.quote.review`、`custom.anbang.report.read` |

页面能力由有效权限计算。销售角色在这份自定义能力描述中没有管理权限，不表示销售无需应用准入或对象、字段、记录授权。特价审批是铵帮的真实业务动作，也不意味着其他企业的非标开发需要额外审批。

当前铵帮用实际销售身份读取用户可见资料；后台受管操作使用配置中的既有管理员，并继续核对业务调用者。技术执行身份不是第四种人员职责。可以借鉴的是识别实际执行者与业务操作者，不能推广成所有企业都要配置管理员后台或三个人员角色。

## 一条端到端链路：测算购车方案

1. 销售在接待中表达需求，智能体根据业务指令确定预算含义和车型条件。
2. 服务工具把业务参数交给处理器，租户与操作者由可信执行上下文确定；该顾客接待场景还使用已绑定的应用和顾客。通用工具协议允许应用、固定目标缺省，其他业务不必复制顾客绑定。
3. 业务服务读取当前用户可见的车型、政策与事实，选择当前采用的函数或算法核算。
4. 平台记录保存结果及业务需要的依据，工具返回实际金额、状态和后续定位。
5. 页面与智能体按同一结果呈现；确认、提供或成交由对应的业务动作另行记录。

其中，平台负责存取与授权，Runtime 负责会话和工具执行，铵帮负责“预算是什么意思、怎么算、哪些条件适用、结果代表什么”。特定品牌算法、收益口径、政策关系属于企业业务。

`agent-definition.mjs` 中的声明经项目导出脚本生成包含 `instructions` 和 `assistantTools` 的业务定义内容；本地导出不会自动更新在线智能体。使用时接续项目实际的定义导入或更新入口，并由宿主装入相应处理器。

铵帮内部金额使用“分”的整数字符串，比例使用显式分子/分母，模型结果提供带单位的展示金额。这是其精确核算的选择。可推广的知识是把单位、精度和输入输出合同说明白；其他业务按自己的数值合同实现。

## 如何借案例完成一个新需求

假设需要增加“按额定功率筛选车型”：

- 模型中声明数值和单位，或复用已经表达这一含义的字段；检查目标元数据与历史记录。
- 查询使用字段合同与平台支持的筛选，缺资料与不符合条件分别表达。
- 页面需要时展示筛选与单位；智能体需要时在查询工具中暴露相应业务参数。
- 为实际使用者配置字段访问，确认两种入口得到一致的业务含义与授权范围。

这类变更复用平台查询；品牌专属计算规则则重点修改算法、输入依据、函数接入与计算样例。

复用模型与代码衔接、能力映射、公共组件及页面/工具共享业务操作的做法。品牌公式、角色、状态、金额表达与部署方式按目标企业选择。
