# 有界状态探索与真实回放

用于异步、重试或持有者切换存在多种可达顺序，手写几个成功和失败案例仍容易漏交错的任务。简单顺序测试足够时沿用原测试。此方法服务原任务的必要验证，不自动建立独立系统测试。

## 从代码确定可探索的顺序

1. 写出用户可观察的不变量及依据，区分临时状态与最终承诺。例如，未结束的发送不能把临时清空的编辑框当成人工清空；独立交互保留草稿时，人工清空仍须有效。
2. 列出能改变该事实的实际参与者、状态和动作。每个动作指向源码入口及读写位置；沿实际调用方确认先后约束，不能只看被调用函数。
3. 按真实执行边界拆动作。读取后跨 `await` 再写入的过程不能在模型中合成一个不可分割步骤；同一同步段内无法插入的外部动作也不能随意交错。
4. 固定本次边界：参与者与请求数量、数据代表值、最多步骤及被排除的路径。状态去重必须保留影响不变量和后续动作的全部差异，不能只按界面标签合并。

小范围可以在项目现有测试中枚举满足前置条件的事件顺序，逐条重置场景并驱动真实实现。顺序增长到不便直接回放时，再选择可复现的模型检查工具；不为一次小验证默认安装完整形式化工具链或新建验证技能。

## 用反例驱动真实代码

先检查初始状态，再探索边及其后置状态。保存每条违规路径的动作与实际结果；从短路径开始，删除不影响违规的步骤，留下最小可复现序列。没有满足前提的动作时，区分正常终态、建模遗漏与真实死锁。安全性质通过不证明最终一定完成；超时、活性与公平性按实际承诺另验。

手写模型的失败只是候选。将反例逐步翻译为真实公开调用、受控返回、时钟或事件，核对每步前提和断言。不能回放时先查模型的原子性、动作前提、身份或替身，不能直接报告产品缺陷。网络或存储替身只能替换原系统边界，不能用测试自己维护的业务状态代替被测实现。

例如，草稿场景至少区分“编辑框清空 → 发起发送 → 旧持有者退出 → 新持有者进入 → 回执”和“回执先到再切换”。有附件时，上传完成与发送 POST 是不同的等待点。探索得出的路径必须实际驱动草稿 API；画出相同状态图不是回放。再检查无发送时的主动清空、保留草稿的独立发送，防止把所有空值恢复成旧正文。

用真实旧版本与修复版本，或隔离副本中的针对性错误变体，确认检查能拒绝目标错误，并保留合法相邻行为。失败时不削弱不变量或缩小边界来制造通过。沿原任务授权决定是否修产品，验证方法本身不授予修复权限。

## 保留可复跑条件

留下运行命令、所测提交或输入摘要、工具版本、动作与源码映射、探索边界、反例及真实回放结果。优先放在原测试或本次证据目录，不建立第二套活动台账。后续覆盖代码、调用方或等待边界变化时，重新核对映射后才复用结果；不能仅重跑旧模型并前移版本标识。

报告明确区分模型结论、真实实现回放和仍未覆盖的环境。有限路径全部通过只证明这组状态与顺序，不证明任意数据、任意并发、完整 UI 或生产系统正确。
