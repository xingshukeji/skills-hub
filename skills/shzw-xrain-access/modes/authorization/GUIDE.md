# XRain 业务权限

用原用户、租户和具体动作复现；403 可能是正确拒绝，不能默认加权。

设计或调整角色与权限集时，按以下顺序工作。单次权限故障直接定位受影响动作，不必重做全部角色设计。

1. 从已确认职责列出角色、业务动作、字段和记录范围，区分平台管理与业务职责。未确认的角色保持待定，不按名称习惯新增。
2. 对照目标实际角色、权限集、成员绑定及内置和自动授权来源。已有内置角色和权限集满足职责时复用；不重复创建管理员，也不假定管理员自动拥有新业务对象的全部权限。
3. 按未满足的动作及范围形成增量方案，说明权限来源与受影响主体。只读请求只交付方案；有变更授权时保留无关绑定，并按下方入口处理替换和冲突。
4. 以原职责核对允许与拒绝的动作和范围。实施后回读实际授权，再用原用户验证相关业务；管理员成功不能代替普通成员的证据。

例如，要确认成员能读取范围内记录 A、不能读取范围外记录 B，先固定原 userId、tenantId、applicationId、动作和两条已知记录，再核对实际字段及符合目标合同的拒绝或过滤。管理员回读角色成功、原人查询返回空列表，都不能证明这组业务范围。只要求调整绑定时可报告配置回读通过；要报告业务可用，还须有原人业务结果。缺少获准对照资料时保留未验证，不为复测另建长期身份。

- 不知道拒绝在哪层：[定位](references/access.md)。
- 新用户、角色调整或撤权：[授权来源与变更](references/authorization.md)。
- 自动化、机器人、代发失败：[执行权限](references/execution.md)。

只修本次获准且符合原职责的缺口，保留其他授权；集合替换前先读取，并发冲突后重新合并。以原用户复测相关允许及禁止动作，不能换管理员证明修复。固定身份先按目标账号规则复用。

通过目标管理页面、受管 API 或已可用 CLI 操作。参考相对本模式目录（Workforce 的 `resourceBase.path + "/modes/authorization"`）；报告拒绝层、授权差异和复测结果。
