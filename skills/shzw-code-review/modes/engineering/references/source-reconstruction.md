# 复原机制的历史约束

用于删除、合并或重写既有机制前，当前调用链仍不足以说明原约束的任务。沿原任务取证；历史调查不自动授权产品修复或全项目扫描。

## 固定需要追溯的语义

复用主入口已有的运行链检查记录，固定本次需要改变的分支、源码版本、实际调用方与等待边界。这是历史检索的锚点，不另建一份架构走读产物。当前行为已足以决定取舍、历史动机不影响动作时，不展开以下调查。

## 再回答为何形成这个机制

当前代码能证明行为，不能独自证明作者动机。针对决定取舍的符号或分支，先找最后改动，再找引入或改变该语义的提交：

```text
git blame -L <start>,<end> -- <file>
git log --follow -p -- <file>
git log -S '<exact text>' -- <file>
git log -G '<pattern>' -- <file>
git show <commit> -- <affected files>
```

`blame` 指向的提交可能只改过格式、类型或清理逻辑。读取语义变更的完整相关补丁、同次新增的测试和提交说明；有明确关联时再查可访问的 PR、问题、决定或原用户消息。只读取会改变本次取舍的来源，不默认搜索所有服务或私有聊天。历史文件、字段改名时继续追原语义，不能因当前名称没有早期命中就认定没有历史。

分开记录直接说明、证据支持的推断与未知。测试可以证明曾保护哪种行为，不单独证明业务方为何要求它；提交存在不证明已发布或仍适用。来源矛盾时保留双方的时间、对象和范围，按现行产品事实解决，不替历史编出一致动机。

## 把发现变成当前动作的约束

准备改变机制时，把相关证据转成四类简短结论：保留什么保证、可以改变什么实现、应避免哪种已失败替代、还有什么风险待核。只保留当前消费者仍需要的保证；旧事故不自动授权新增兼容、门禁或永久状态。

选择最便宜且能区分取舍的真实检查。例如，流上已关联的完成事件先于 HTTP 回执时，顺序等待回执会改变完成语义；资源释放修复不能据此删除并行观察。运行原回归或一个针对真实实现的探针，核对这一保证与当前源码仍一致。已充分成立的静态证据继续有效，不把无法运行的结论伪装为实测，也不因缺少无关历史阻断其他工作。

向原任务返回影响决定的来源、上述约束与证据缺口即可。不要求另建架构文档、历史台账或审批步骤。
