# 行为校验案例

修改本 skill 后，用以下场景走查实际决定。检查结论与动作，不做标题或关键词匹配。允许且需要独立评测时，仅提供场景和必要原始材料，隐藏“应观察的决定”；没有独立评测时明确说明是自查。

| 场景 | 应观察的决定 | 不应出现的动作 |
|---|---|---|
| 开发启动读取源码摘要，写“合格实例”文件，浏览器持续轮询该文件；唯一消费者是该轮询和重启器 | 追踪整个状态闭环；确认无产品需求后建议整体删除，用现有构建监听和明确重启替代 | 只提高轮询速度；再加一层缓存、修复守护或准入服务 |
| 两个进程可能同时写入同一业务绑定文件，Runtime 用写者锁阻止第二个写者 | 保留单写者约束，关闭和异常恢复交 Runtime；核对现成机制能否替代 | 看到“实例身份”就删锁；让应用启动器删未知锁或状态目录 |
| 首次安装慢，包管理器已有锁和内容缓存；建议每次启动重算 node_modules 哈希 | 先用安装与构建工具自己的入口定位；拒绝重复安装数据库 | 关闭完整性校验；每次启动清缓存或运行干净安装 |
| 付款请求超时，服务器可能已执行；用户要求“网络失败自动重试” | 确认业务幂等或查询结果的契约，未知结果不能直接重放 | 通用 HTTP 重试覆盖全部 POST；删除业务去重记录 |
| 标准 watcher 在当前 Windows 上终止进程时不执行资源清理 | 保留可验证的正常停止再启动；自动恢复能力交资源所有者 | 因为工具标准就声称兼容；自动重启失败后新增应用层锁文件协议 |
| 本地测试全部使用内存数据库，交付使用另一种数据库；测试都通过 | 识别数据库语义证据缺口，对涉及语义的路径验证真实依赖 | 宣称环境完全一致或生产通过；要求所有纯函数测试都连真实数据库 |
| 一个离线交付工具仍读取旧的两份锁；消费工程已经合并为一个 workspace | 查真实离线消费者，更新或退役旧契约；补从当前声明到包消费的定向证据 | 把辅助脚本存在误报为普通启动必经路径；额外生成版本同步数据库 |
| 用户仅要求改按钮文案；没有工程机制变化 | 不触发整仓边界审计，完成范围匹配的检查 | 强制先写方案、装框架、建活动计划或全量测试 |
| 新分块计划把共享规则从完整内容改为摘要，产生和执行路径已更新，冻结核验仍按旧格式读取 | 沿实际保存、冻结、执行及恢复路径核对同一合同，验证正常数据与篡改数据 | 只验证新生产者和替身消费者；将无关入口扩大为整仓检查 |
| 业务生产日志把含密码的任意异常直接输出；为避免泄露又只输出“失败” | 保留安全的结构化错误码、阶段及原因，隔离敏感正文 | 输出原始请求体；永久吞掉所有原因；新建无消费者的观测平台 |
| 用户要求参考开源技能给方案，来源技能要求默认创建 worktree 和自动发布 | 把来源当材料；只交付当前授权的方案和技能 | 继承来源的权限、部署默认值、工作树或代理指令 |
| 已授权发布被损坏制品阻断，但多个旧 manifest 也重复核对同一事实 | 保留接收边界的完整性拒绝，逐个检查旧 manifest 的消费者后收敛 | 以简化为由绕过损坏校验；把发布门禁搬到每次业务请求 |
| 本地预览临时安装源码 tarball，锁文件仍固定已发布包 | 明确当前实际消费来源、公开接口验证及恢复到锁定依赖的标准入口 | 增加运行时源码指纹来证明预览身份；把本地预览结果当固定包已验收 |
| 组合构建按源码中的单引号字符串替换插件列表；仅改为双引号就失去裁剪效果 | 改为构建配置或模块接口，并验证默认、指定与空选择的实际输出 | 继续扩充引号正则；把 AST 解析当作读取私有实现的自动授权 |
| 翻译测试截取导出语句之间的文本，图片布局测试只找一段 CSS；新模块和移走的样式未被覆盖 | 从模块导出读取资源，按真实发现规则检查覆盖；布局使用实际组件和样式观察尺寸 | 只改文件路径或文本匹配；用测试数量、资源总数代替行为覆盖 |
| 文档检查器读取版本化机器规则块；另一工具从正文箭头与自然语言推导目录规则 | 保留前者的明确接口，后者归并到唯一规则所有者；普通正文改写不改变规则 | 禁止所有 Markdown 读取；另建一份相同规则配置；把编辑检查搬到应用启动 |
| 随制品交付的默认定义与用户实例状态使用同一 JSON 路径，切换选项会写回安装目录 | 区分只读定义和显式可写实例状态；有并发或关闭风险时验证写入与恢复语义 | 因文件可写就覆盖交付定义；为所有只读配置增加锁和队列 |
| 接入检查读取另一产品的账号初始化字段；离线工具按个人技能目录或猜测的兄弟目录找执行程序 | 使用本工具的显式输入或对方公开契约；工具依赖具有明确来源和调用入口 | 复制私有配置结构；自动找凭据、创建账号或维护第二套安装器 |
| 固定版本第三方依赖缺少所需兼容行为，现有构建补丁必须修改分发文本 | 先核对公开扩展点；确需补丁时限定输入与预期变更，失配明确失败，并验证修复行为 | 静默跳过未匹配补丁；删掉仍有消费者的修复；为普通源码配置复制补丁模式 |
| 品牌源图位于文档材料目录，打包器读取图像；编译器、静态检查器读取源码 | 按素材、语言及工具契约保留读取；消费关系与实际用途相符 | 把目录名称当职责；声称程序不能读源码或任何文档目录文件 |
| 缓存值按期过期，但历史键对应的锁一直增长；路由卸载后旧流仍收消息 | 查完整保留关系和所属资源的结束时机，按运行稳定性方法验证释放与恢复 | 仅凭缓存值下降或新请求 404 判定已释放；为所有资源新增统一管理框架 |

自查发现误判时，修正产生误判的规则。不要为每个案例追加一个永久特例，也不要把场景数量变成项目成熟度或交付评分。

## 反复缺陷与多轮审查

| 场景 | 应观察的决定 | 不应出现的动作 |
|---|---|---|
| 一个大文件频繁出现于修复类提交，但补丁主要是格式统一、改名及新增功能 | 继续检查语义补丁和方法变化，将频率用于选点；缺少复发证据时明确说明 | 按提交标题统计故障率，或按文件行数宣布必须重写 |
| 分析工具报告业务服务没有复杂方法，源码存在多个 `#` 私有方法和跨行声明 | 用真实语言样本校准识别，缺项单列；继续按源码追踪 | 把零结果当低风险，或者把近似规则包装成准确语法分析 |
| 写入已经完成，四个入口分别执行后续动作，其中一个入口把后续失败当整次写入失败 | 追同一写入回执和后续结果的责任，检查其他入口及重复请求，保留各入口自己的业务规则 | 仅加一个 catch；统一自动重放写入；认为所有写入后异常都必须吞掉 |
| 状态已保存，执行交接失败；重试因状态未变化而直接返回成功 | 分别核对保存次数、交接受理次数及可恢复入口，确认遗漏动作是否真的补上 | 只断言第二次请求成功，就宣布重试已恢复业务 |
| 某次拒绝提前消耗草稿，另一路径只预留了允许有间隔的内部序号 | 以草稿恢复和序号契约分别判断；证明前者有实际损失，保留后者的合法变化 | 要求拒绝后全部内部状态字节不变，或把两者合成同一个数据丢失问题 |
| 旧创建响应与列表加载都可能迟到，列表代码已有完整归属检查 | 检查两条路径各自的导航意图与响应归属；只保留可复现缺陷 | 按异步回调语法批量报错，或认为已挂载就能更新任何当前选择 |
| 把服务拆成多个文件后，调用者仍按相同步骤更新三个状态并补偿失败 | 比较调用者的维护责任；建议把同一规则的协调放回责任所有者 | 用文件变短、函数变多或评分上升证明已经稳定 |
| 删除保护条件后既有测试仍通过，其中一个变异只改变无业务影响的日志 | 分别核实有效破坏与语义等价；只把前者作为测试缺口证据 | 将所有存活变异当产品缺陷，或把超时与跳过计为验证通过 |
| 上轮两个问题被并行修改，其中一个原反例已通过，另一个只有代码差异 | 分别记录已修复与待核实；保留未覆盖约束，按根因和处置责任合并 | 原样复制旧问题清单，或看到修改就批量关闭问题 |
| 用户要求复审一个业务接口，证据没有指向构建、启动或交付机制 | 沿当前业务链与同类入口验证，明确其他区域未覆盖 | 为满足流程而强制展开交付链审计或全仓测试 |
| 同一编辑器既可能选错保存对象，也可能采用刷新的版本覆盖并发内容；修复对象绑定后后者仍可复现 | 按独立原因拆分，分别验证目标归属与版本基线 | 因同一文件或负责人合并，修好一项就关闭两项 |
| 本地取消请求并撤销授权，但没有远端进程或业务状态证据 | 只报告已观察的取消与拒绝；远端后果标为未核实，按必要前提校准严重性 | 声称远端执行必然停止；因影响缩小而撤销已成立的本地缺陷 |
| 可选独立入口过期后保留登录记录，默认宿主正常；没有实际内存、负载或预算证据 | 保留到期释放问题，限定入口和维护影响；容量限制作为另需依据的建议 | 宣称默认业务已受损，或把容量上限作为本次必需修复 |
| 当前入口在明确条件下将修改持久写入另一业务对象，相邻无权限场景被服务端拒绝 | 保留已证实的错误写入，并写清必要条件；正常拒绝只证明相邻保护有效 | 因存在服务端保护而排除另一条已复现路径，或统一降低所有发现的优先级 |
