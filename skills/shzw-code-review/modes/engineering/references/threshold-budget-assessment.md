# 门槛与资源预算评估

从用户能否完成正常操作出发，系统找出会拒绝、阻断、限流、隐藏或禁用操作，或引起超时、过期、丢弃、强制重试和重新同步的机制。评估同时考虑实际资源、业务结果与保留的保证，不把搜到的数值直接当作缺陷。

## 触发与边界

用户明确要求全面或逐项评估时，按其指定对象、范围和授权直接开展。用户只讨论某个资源预算、限制或超时时，先处理当前问题；系统评估可能有帮助时，可简短提示能对当前项目再做一次类似评估，不以此要求用户中断当前任务。用户已经要求评估时不重复询问是否开展。

先固定评估对象、工作副本和实际运行或交付来源。覆盖范围以用户要求和真实消费者为准：完整项目可包括服务端、Web、桌面、移动端、独立应用，以及实际使用的配置、启动和交付入口；跨项目只追踪实际依赖与责任方。局部评估不冒充全项目结论。分批调查时保留范围和待查入口，不能由发现清单反推覆盖完整。

评估可使用授权内的源码、配置、测试、既有日志及必要的本机隔离复现和资源测量。只读评估与建议不自动授权产品修复、共享环境变更、独立系统测试或部署；已有后续实施授权时按其范围接续。

## 盘点并追踪到用户动作

按实际入口枚举机制：数量、字节、输入和上传、并发、队列、连接、缓存、分页与批量、速率、超时、有效期、重试和冷却，以及身份、状态和其他操作前置条件。沿输入、传输、执行、结果和恢复追踪配置、默认值、覆盖顺序及消费者；搜索关键词只是发现线索，不能代替核对实际可达路径。

同一底层预算在多层重复出现时归并记录，并保留各层作用点与消费者；不同资源或不同业务保证分别记录。区分业务准入、实际资源预算、分页或显示窗口、缓存目标和调优参数：每页上限不一定是总数据上限，缓存目标也不应直接被视为允许的业务对象总数。

对每个机制记录：

- 代码及配置位置、生效入口与对象范围，如单次请求、连接、用户、租户、工作线程或进程；默认值、覆盖方式和当前实际生效条件。
- 资源或业务事实的真实所有者，机制保护什么，数值与保护方式有什么负载、契约、故障或测量依据。
- 达到门槛时原用户看到什么、数据及后续操作怎样变化，以及应被允许的相邻场景是否被误伤。
- 当前证据属于已发生、已复现、仅静态可达或未验证；同时记录反证、责任项目和缺失的最小验证条件。

## 逐项判断与交付

先检验机制本身是否必要，再决定数值；没有独立依据的重复门槛优先评估删除或合并，不先放大数值，也不先增加恢复协议来补偿不必要的限制。对确有资源保护需要的机制，结合实际负载、资源成本、回收与背压、取消和恢复，区分活动资源、闲置缓存、峰值和稳定占用。必要时选择能区分正确与错误行为的最小测量，不把短时间样本说成长期容量结论。

每项选择删除、合并到真实资源所有者、调整预算、保留或证据不足，说明理由、用户影响、必须保留的保证和验证动作。身份鉴权与授权、真实并发冲突、数据完整性及实际平台协议各自核对；删除不合理门槛不等于删除这些约束，也不预设一切资源都不设边界。

例如，某协作服务曾把主服务的频道缓存目标当成频道总数准入，导致合法频道读取被拒。可评估删除该重复准入，同时让实际持有数据库连接的工作线程管理连接预算并及时释放闲置资源，保留鉴权和消息交付；这个案例不能推导所有缓存或连接预算都应删除。

最终说明完整覆盖范围与未查入口，提供归并后的逐项清单、按真实业务影响排序的问题、预算依据与取舍、证据状态和责任方。缺少依据的项目给出下一验证动作；既有项目结论与历史数值仅作调查线索，应按当前版本和负载重新核对。已修复且证据仍适用的问题记为已处理，不重复当作未修复。
