# 语言与运行时审查

用于系统检查语言、框架和库特性在规模、并发或持续使用下的影响，也适用于用户所说的“代码能跑，但缺少工程深度”。沿用主技能的范围和授权；不因代码可能由 AI 生成而认定缺陷，不把代码审查自动改成生产压测或升级任务。

## 从反馈得到项目检查项

1. 固定实际技术栈、运行模式、依赖锁和当前消费版本。源码、已安装包、公开导出和运行制品分别核对。某语言只出现在依赖或文档中，不证明服务使用它的调度模型。
2. 按当前调用机制查官方文档、对应仓库的 issue、discussion、修复提交和版本说明。记录复现条件、适用版本、修复状态及本项目是否满足前提。帖子、市场叙事和相似 API 名称只提供调查线索。
3. 把适用线索放回主技能已有的检查记录：真实入口与消费者、数据规模或并发交错、预期与实际、反证、责任位置和验证。局部任务只查命中链路；系统审查则逐项给出确认问题、已查未发现、不适用或证据缺口。
4. 从命中符号扩展到别名、包装器及同一状态的其他读写入口。搜索用于找位置，不能把 `.Result`、`sync`、`cache`、`...items` 等命中直接计为缺陷。
5. 分别报告直接观察、推导影响和未确认条件。复审允许撤回误报、降低或提高定级，并保留理由；不用原发现数量约束结论。

例如，JVM monitor pinning 要核对 JDK 和虚拟线程使用；JDK 24 的相关变化不能用来推断所有 native/JNI 等待已经消失。.NET、Node.js 或原生客户端也不能直接套 JVM 结论。Jint 的历史异步问题和最新文档，应分别对照项目锁定版本，不从旧 issue 判定当前能力，也不据新 API 建议直接升级。

## 沿实际入口筛选

| 机制 | 要核对的触发与反证 | 修复方向需要保留什么 |
|---|---|---|
| 异步 I/O 被同步等待 | 沿 `.Result`、`.Wait()`、`GetAwaiter().GetResult()` 和宿主 SDK 追到未完成 I/O、线程种类及嵌套调用；已完成内存任务与纯 CPU 工作分别判断 | 优先可等待调用链；旧同步脚本不能机械加 `await`。确需隔离时由执行所有者维护有界资源，不能用无限新建线程或只提高通用线程池最小值充当修复 |
| 主线程计算与同步 I/O | 时区逐分钟枚举、正则、解析/序列化、同步 SQL、排序或每个流事件重算；是否为每个输出重复扫描全部历史 | 先修算法或查询形状，再按剩余成本选择 Worker。按实际依赖复用未变化的历史结果，语言变化仍更新文案；保留结果、顺序和时限，异步函数名或搬到 Worker 不证明成本消失 |
| 查询只需局部却加载全部 | 查最新状态或存在性是否先 `.all()`/`ToList()`/解析全部历史；JSON 条件是否可用索引，目录并发是否同时占满所有仓储槽位 | 用 latest、EXISTS/LIMIT、适用索引及有界并发；核对查询计划、写后索引维护和旧库重开。不为局部成本擅改公开分页协议、加状态列或删历史 |
| 长数组展开为实参 | `Math.min/max(...values)`、`splice/push(...values)`、`apply` 的输入能否持续积累；是否已经持久化才发生内存更新异常 | 消除实参数量依赖；核对空集、NaN、正负零、序号和排序。保留完整历史，实测触发长度不成为产品容量上限；数组引用替换先查持有者 |
| 时间与数值语义 | 当地日期和 UTC、夏令时缺口/重复时刻、工作日、半小时或小数时区；序列化后的数值精度和类型是否仍满足 DTO | 使用当前版本可用的成熟机制并与旧规则对照；“较晚时刻”和“缺口后的第一个有效分钟”可能不同，固定加 24 小时不是等价转换 |
| 等待后的准入提交 | 数量或版本检查后是否经过 `await`、回调或钩子；两笔都通过检查时能否共同超额或覆盖状态 | 优先让相关所有者顺序消费；已有配额按最终去重集合和实际持有阶段核对，确需独立预留时再维护在途占用。验证失败、取消和关闭，不把不同用户全局串行化 |
| 分层协议容量 | 完整目录、单批、累计订阅、帧大小、连接缓冲、全局频道、Worker 仓储是否采用不同限制；首个异步核验之前是否已积压工作 | 先核对标准流、连接和执行器的背压及生命周期，再查完整业务通知与恢复。轻量关系与重状态分别持有；分批、放大一个常量或只订阅当前项都可能破坏合同，也不默认给每层补一套预算 |
| 缓存值与辅助注册 | TTL 后谁仍持有 key、context、角色集合或对象；索引是否还用于活动注册、后台刷新和预热；缓存 miss 是重建还是失败关闭 | 先确认各自生命周期及代价，不能仅凭“值 miss、索引仍在”确认泄漏。需要回收时验证替换、迟到回调、显式失效及合法租户，不照抄别的缓存策略 |
| 线程、回调与上下文 | 长期线程启动是否继承首个请求；队列、最近任务、闭包或异步上下文是否留住最后请求；取消是否仍有运行中副作用 | 公共执行资源不永久保存调用者；每项执行仍正确传递身份、租户、事务和跟踪。结束工作后释放捕获，不用全局禁止上下文流动修局部保留 |
| 流、连接与订阅释放 | 响应体是否消费或取消，reader/stream/socket/定时器是否沿正常结束、导航、异常和关闭释放；重试或监听是否重复注册 | 同一所有者安排释放，保留关闭次序、迟到回调保护和必要持久结果；不依赖 GC、重启或删除状态目录来证明正常回收 |

## 复现与定级

先证明相同入口的正常小规模行为，再构造能暴露差异的规模、等待或交错。使用项目实际模块；需要 SQL、协议或浏览器差异时补真实 SQLite/目标数据库、传输或浏览器证据。Node 下的 V8 复现不自动等于完整浏览器页面或原生端已验证。

对照固定同一代码阶段、运行时、数据形状、调用次数、并发、时延来源与资源配置。解释器加模拟 SDK 的结果不能与裸 `Task.Delay` 换算为候选加速比；人工慢 I/O 能证明线程占用机制，不能单独证明生产发生线程池饥饿。保留实际请求未发出、超时和失败样本，不只看成功平均数。

用事件循环延迟、线程种类/等待栈、查询计划、保留对象和业务结果分别支持对应结论。对象滞留、RSS 上升或无 OOM 不能互相替代。GC 保留测试应结束创建对象的栈帧与异步助手，避免测试本身持有对象；它不代替自然运行周期观察。

把测试失败分为产品断言、夹具/调用合同和清理钩子失败。先确认测试传入真实请求字段；不能给生产接口增加静默默认值来满足过期夹具。Windows SQLite 文件繁忙时，追服务、插件、连接与钩子执行顺序；先关资源再删隔离目录，不能据删除失败直接宣称线上流泄漏，也不能重试删除来掩盖仍打开的资源。

## 再审修复方向

修复方案和实现都作为新候选审查，沿原业务动作查其增加的状态、协议和资源。按实际变化选择以下检查，不为普通小改强制引入执行池或队列：

- 选择并发与保留机制：先查标准流顺序读取、背压、现有连接及任务退出能否控制在途工作。增加自定义预算前，说明独立业务或资源依据、现成机制缺口和计数维护成本；异步处理后半段的计数不能保护前面的等待。标准流还须验证消息边界、错误恢复、关闭及其他连接并行。用户明确删除配额时，移除相应计数和旧拒绝断言，按新约定验证，不照旧上限验收，也不顺带删除无关保护。
- 新增执行资源：根任务与嵌套任务是否争抢同一批已阻塞的线程，异步后重入是否丢失归属。先确认是否需要自建队列；确需应用持有排队数据时，才按独立依据检查数量、单项大小与总字节，固定小项可据数量换算。空集合等小请求同样可能积累等待节点。
- 新增取消：排队任务可撤销不等于运行任务已停止；不能在业务清理、提交或回滚仍进行时提前向外报告结束。核对取消、异常和资源关闭的实际后置结果。
- 新增协议：发送者、接收者、目录和存储的限制是否一致；替换或退订是否只影响本连接；排队、发送中及未 ACK 的数据何时释放；回收后 epoch、重放与未读是否仍正确。
- 新增缓存或回收：是否改变正确的预热、授权和 miss 行为；修复保留关系时不顺便删除业务状态或扩大身份。
- 改变保存方式：写失败保留旧状态，成功后内存、磁盘与重开读取一致；不能把同步文件写改成无序异步写，引入临时文件或写者竞争。
- 改变库或公共接口：识别所有直接消费者，用其实际包版本、锁、公开类型和候选包执行验证。编译自己的源码不证明应用已消费，构建和 Git 推送也不等于发布或部署。

验收同时覆盖原反例、同类入口和依赖旧行为的合法场景。对超出本轮证据的生产负载或长时结果保留边界；不要靠取消业务功能、截断历史、自动扩容或新增无法解释的上限使测试变绿。
