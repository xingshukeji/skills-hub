# 工程职责边界

让每项工程机制有可核实的需求、责任方和执行时机。优先减少需要长期维护的状态、协议和操作步骤，同时保留真实业务、平台协议及数据完整性约束。目标不是最少代码行数，也不是所有环境拥有完全相同的工具。

## 适用范围与交付

先确认本次要调查、提出方案还是实施。沿用用户已经确认的目标、授权和取舍；分析请求不授权修改产品、清空状态或发布。若已有方向对齐结果，直接消费它，不重复制造审批。

局部变更只查受影响调用链。沿[主入口](../../SKILL.md)的检查记录，先确定当前用户动作、正式判断规则及实际入口，再浏览[审查维度](references/review-map.md)筛选适用工程机制。将命中项落实为入口、消费者与可观察场景；不适用说明依据，未执行的适用项保留待查。已有业务依据时直接复用，不重复路由，也不将整表强加给局部修改。

按需读取其他材料：

- 系统梳理语言特性、运行时性能陷阱或 AI 生成代码的工程隐患时，读[语言与运行时审查](references/language-runtime.md)。先核对技术栈和实际版本，再把上游反馈转成可达检查；同步审查拟议修复会增加的状态、容量和兼容责任。来源是否由 AI 生成不代替行为证据。
- 用户要求检查反复出错的文件或方法、解释修复遗漏、比较重构效果或合并多轮审查时，读[反复缺陷审查](references/recurring-defects.md)。先用历史定位，再证明业务规则被怎样破坏；不从提交次数或复杂度分数直接判定缺陷。
- 新增、修改或审计文件消费关系时，读[文件消费职责边界](references/file-consumption.md)，确认消费者使用的是文件承诺的接口。
- 比较外部方法或选择现成工具时，读[开源方法与适用边界](references/open-source.md)，并核对当前工具版本。
- 审查资源增长、缓存/队列容量或退出释放时，按[运行稳定性](https://github.com/xingshukeji/skills-hub/blob/main/skills/shzw-testing/modes/stability/GUIDE.md)选择相关测量与恢复场景。本 skill 负责确认资源所有者、保留关系及失效与释放时机；容量约束需有负载、资源预算或明确契约依据。
- 新建或实质修改本 skill 时，用[行为校验案例](references/behavior-cases.md)检查误删、过度保留及越界实施。

## 建立事实

从用户实际入口追踪到消费者，覆盖相应的源码、公开接口、类型、测试及运行说明。搜索关键词只用于定位，不能据 `hash`、`development`、`retry`、`cache` 或文件行数直接判断好坏。

记录会影响判断的运行事实：入口调用了什么、读取谁的配置、谁写入状态、谁消费状态、失败由谁处理。区分已提交基线、正在修改的工作副本和实际运行制品。其他任务已经修改的机制不能继续当作原状，也不能仅凭修改存在宣称验证通过。

系统性调查沿受影响的用户操作链展开；涉及构建、启动、依赖或交付机制时，再追踪对应的构建到运行链。检查正常操作及相关的失败、停止、重启、升级路径；没有需求或证据的路径标明未核实，不扩建机制来填满表格。

## 文件消费职责

先根据生产者、正式用途和实际消费者判断文件职责，再检查消费接口。扩展名、目录、可读取或可写入，都不能单独证明它是配置或允许被当前组件修改。对同一文件中的程序、数据与说明分别判断；例如声明式源码和运行状态都可能使用 JSON。

沿受影响调用链核对：谁产生文件，谁在何时读取哪部分，依据什么接口解释内容，以及谁可以写回。配置消费命名字段，源码消费公开导出或语言结构，文档消费明确的文档协议；不得把偶然句式、引号或源码位置变成隐含的配置接口。构建、静态分析和文档检查可以按各自职责读取文件。

交付定义与可写实例状态分别确定所有者。测试验证消费者的实际输出和保留的不变量；源码文本相同不能代替行为证据。依赖补丁等确需处理文本的情形，按[文件消费职责边界](references/file-consumption.md)限定输入、失配处理和验证，不推广为普通文件消费方式。

## 判断机制是否必要

对每个可疑机制回答下面的问题，答案可合并成一条简短记录：

1. **依据是什么？** 指向用户要求、具体消费者、平台契约或已复现故障。区分已确认要求、实现事实和工作假设。
2. **拿掉会发生什么？** 说明具体损害及触发条件。检查是否只会失去该机制自己生成的标记、清单、评分或准入状态。
3. **谁拥有责任？** 找能控制该事实并执行修复的组件。不能因为应用最容易改，就让应用代管包管理器、运行时或部署入口。
4. **何时必须执行？** 区分安装、构建、测试、发布、启动、请求及显式维护；后一个时点的需要不自动成为前一个时点的门禁。
5. **谁提供现成能力？** 先查当前使用的框架和工具，再比较适合的开源方案。核对真实平台兼容性、关闭语义和维护成本，不以“标准工具”代替验证。
6. **状态是否值得存在？** 对新增文件、表、缓存、锁、队列或状态机，找产生者、业务或运维消费者、失效条件和恢复责任。只服务自身检查的状态优先连同机制删除。

判断准入是否过严时，先确定合同约束的是一次调用、某个使用场景还是整个定义，并查当前生效的输入、输出和使用范围。用符合该完整范围的样例证明误拒；单次调用成功不能单独证明整体资格有效。若已确认的合同本身增加了不合理成本，单独说明其业务影响和可选改动，不把依约拒绝当作实现缺陷；用户后来改变目标时按新目标判断。

非业务机制可以合理存在。可复现构建、必要诊断、制品接收完整性、授权、数据并发约束和兼容承诺都可能构成独立依据。它们必须能说清所保护的事实，不能只用“更稳妥”“生产级”证明必要性。

从以下处置中选择，并说明证据：

| 处置 | 适用条件 |
|---|---|
| 删除 | 无独立需求或消费者；或被其他所有者完整覆盖，删除后的行为仍满足约束 |
| 交还现成工具 | 工具已有对应能力，且当前版本和平台能够满足必要语义 |
| 移交责任方 | 需求真实，但当前组件不能拥有事实或修复生命周期 |
| 保留并简化 | 需求、所有者和执行时机成立；只去掉重复或不必要的实现 |
| 暂不决定 | 缺少消费者、兼容或故障证据；给出最小下一步调查，不把未知写成缺陷或保留理由 |

检查可以出现在多个边界，但每处必须保护不同的信任、数据或生命周期条件。客户端输入提示不替代服务端授权；下载完整性与业务数据并发校验也不是同一种责任。不得把“一份事实”简化成“整个系统只能校验一次”。

## 对齐开发、测试和生产

以同一产品及交付单元比较环境，不把不同产品形态强行合成同一宿主。核对相同业务入口、配置含义、认证授权、数据语义、公开依赖接口和生命周期。地址、凭据、规模、调试及构建监听可以不同；环境名称不应隐式创建身份、改写权限或改变业务规则。

开发可以编译正在修改的源码。交付验证应覆盖实际打包结果及公开导出；同一目标平台从测试到生产的同一次晋级应使用同一确定制品，运行配置另行提供。多平台分别固定产物；若前端嵌入了环境值，明确其制品影响，不能声称只改配置。

测试替身可以验证局部逻辑；涉及协议、数据库或服务语义时，增加匹配风险的真实依赖证据。不要让 mock 成为另一套产品实现，也不要把替身通过写成真实联通或生产通过。

安装、构建和发布分别拥有自己的失败条件。正常运行不应依赖源码 checkout、文档、制品仓可用性或 CI 过程状态，除非产品确有相应运行能力。依赖恢复和版本升级走既有入口，不在每次启动时重建安装状态清单。

进程管理器负责启动和监督；应用或 Runtime 负责关闭自己持有的连接、任务与持久资源。工具的自动重启若不能满足正常关闭，先保留可验证的正常停止再启动，不以删除状态锁或应用解析别人的锁格式补洞。

## 形成改动与验证

把同一机制的生产者、消费者、恢复代码、测试及说明一并处理。不能只删除一个检查，却留下依赖其状态的重试、清理或旧准入路径。历史兼容只有真实消费者、已有数据或明确承诺支持时才保留；同时说明退出条件。

逐项指定验证观察：哪个用户动作或故障得到什么结果、由谁拒绝、持久数据怎样保留。验证原问题和保留的约束；静态检查、编译、接口替身、真实依赖和目标环境结果分别说明。

保留有意义的既有测试；删除只证明被淘汰机制存在的断言。新增测试应能发现实际行为回归，不通过源码字符串、内部清单存在或测试数量冒充效果。轻微可逆调整不为遵循模板而新增测试。

错误处理保留可安全记录的原因、阶段和关联信息，用户界面只显示用户可以判断或处理的内容。不要原样输出凭据、请求体或任意上游错误。重试须有可重试条件、总时限及结果未知时的处置；非幂等写入不得因网络失败直接重放。

## 输出与持续使用

先给出结论和覆盖边界，再提供紧凑的“机制—证据—处置—责任方—验证”表。涉及持久状态、公共接口或用户操作变化时说明兼容影响。按可独立交付的结果排序，不使用虚构成熟度分数或固定工具清单。

设计时判断必要性，实施时检查新增状态和边界，评审时核对净增加的维护责任，验收时观察用户结果。利用现有评审、测试和事实文档承载结果；不要求每次生成报告、登记任务或安装新框架。

本 skill 不新增运行时准入、开发状态服务、治理数据库、自动发布或整仓重写。它也不授权子智能体、其他会话消息、生产操作或账户变更。需要这些动作时，沿当前任务已有授权和工具规则处理。
