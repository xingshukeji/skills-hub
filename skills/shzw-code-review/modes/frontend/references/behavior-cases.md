# 前端评审相邻判例

用相邻合法场景检查方法是否过度套用。判例帮助作者自查；不代表已执行独立评估，也不规定每次评审的页数和问题数量。

| 输入或证据 | 应有判断与动作 | 不成立的做法 |
|---|---|---|
| 用户要求逐页 review 已给出的整组截图；初看没有遮挡或溢出 | 逐张看原图，检查信息占比、排版、层级、识别与反馈，记录每页问题或保留依据；真实交互另补证据 | 用缩略总览、源码检查或“都正常”代替逐页审美判断 |
| 页面顶部多个标题、卡片和导航，把主表推到首屏下半部 | 用具体位置说明主内容被挤占，找重复层级；保留有独立业务意义的上下文选择 | 套统一首屏占比，直接删掉品牌或业务分类 |
| 应用卡片中次要操作把说明挤成短行；同一应用在两个入口使用不同图标 | 调整主次及可用宽度，核对稳定身份和窄屏；保留已有合法动作 | 只换颜色，或为辨识度给每页设计一套新图标 |
| 只有一张静态图，按钮呈蓝色，界面有动画设计 | 可以审可见层级；校验、反馈时序和流畅度保持未验证，提出对应最小补查 | 从按钮颜色推断权限或校验漏洞，宣称动画流畅或整站无障碍通过 |
| 管理员排障页面必须识别技术 ID；复杂表格在手机局部横向滚动 | 依据任务保留标识与合理滚动，核对可读名称、上下文和操作可达性 | 把所有技术 ID 和横向滚动一律判为缺陷 |
| 表单有清晰焦点边框，Esc 关闭后回到原按钮；另一空态只表示未选择记录 | 记录这些保留项；空态提示选择已有记录即可，不必创建新对象 | 为整洁移除焦点，或给所有空态增加创建按钮 |
| 用户只要求调整一个按钮文案，或 review 无画面变化的 API diff | 保持原任务范围，核对受影响内容和行为 | 启动全站截图、要求设计问卷或独立系统测试 |
| 用户已授权修复一组视觉问题，改动后只有构建通过 | 继续检查新版本对应画面、视口、状态与受影响消费者，再交付；无法复验处如实报告 | 停在“是否修复”，或把构建和测试数量当视觉完成证据 |
| 用户要求参照获奖级网站；首轮修复后仍有明显断行、层级竞争或生硬反馈 | 按八个品质维度继续自检，完成范围内明确可改的问题并复验；用具体收益判断是否继续 | 只在文档里列奖项名称，做完一轮就停止，或把已授权的明显问题推成可选优化 |
| 同页一个遮挡已修复，另一个主操作仍难发现；后者只在旧截图可见 | 分别记录问题影响、证据版本和修复状态，核实当前画面；评审报告可完成，页面是否通过另判 | 用“已修复”概括全页，把待核实当低优先级，或因报告完成宣称页面通过 |
