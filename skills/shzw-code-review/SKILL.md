# 代码与工程审查

从当前项目的真实业务入口判断缺陷，给出可达触发、违反的规则、影响与责任代码。项目源码和命令由目标项目入口定位；技能安装位置不代表被审查项目。

## 先恢复范围，再建立业务依据

只读 review 保持只读；“请修复”接续已确认问题实施，“再 review”复查原范围。已有实施授权中的自查结束后继续原任务，不停在建议。新要求只改变命中部分，已接受的业务目标与约束继续有效。

从当前产品入口、路由或构建消费证明代码仍在使用。指定 diff 检查变更和直接消费者；项目审查从当前业务链选范围。逐文件或多轮检查按用户要求展开，但先知道每个文件服务哪个当前动作。

把本次关键操作写成可检验的业务判断：谁对什么对象做什么，允许与拒绝由哪条现行规则决定，结果由谁保存，下一环节如何读到。读取目标项目的具体契约与下表命中的平台资料；不能以“检查权限、异常、闭环”几个词代替实际规则。

## 核对平台复用与实际运行

XRain 业务先查对象自带字段、Owner、分享、历史、有效授权和已配置的函数/编排；新增同类表或处理器时，核对是否确有独立业务事实。不能只审新代码内部正确，却漏掉重复造平台能力或绕过现有授权的设计。相关语义按需读[对象基础](https://github.com/xingshukeji/skills-hub/blob/main/skills/shzw-workforce-business-development/references/object-foundation.md)与[授权](https://github.com/xingshukeji/skills-hub/blob/main/skills/shzw-workforce-business-development/references/authorization.md)。

Workforce 公共改动追到实际应用、页面和工具，身份链区分认证主体、租户成员及执行绑定。核对消费者安装的包和锁文件，源码已改不证明当前应用加载了它；元数据、HTTP 返回、SDK 转换和页面保存须接得上。内部审查可追责任源码，业务消费者只靠公开能力也应能完成。界面中的状态和解释须服务用户业务判断，不能把内部职责说明当作产品功能。

## 沿消费者找遗漏

先枚举受影响入口，再追调用和状态。公共身份、会话、缓存或保存机制的修复，搜索所有实际消费者；同一对象的查看、编辑、重试和后续处理可能走不同入口。对异步结果核对发起与完成时的主体、对象、版本及页面或执行生命周期，选择真实可达的切换、取消、失败和重试分支。

例如，保存按钮禁用只保护该按钮。若侧栏仍允许离开，必须继续追保存回调能否修改新页面的导航和草稿。这个例子证明要检查实际可达的旁路，不要求所有业务机械套用同一检查表。

每个候选问题都找反证：入口是否退役、调用方是否已保护、后置状态是否会纠正、正常相邻场景是否依赖现行为。已退役内容改查构建、路由和交付残留，不将其界面问题当作当前用户缺陷。严重性由可达影响决定；没有实际负载和预算证据时，不凭容量常量认定资源问题。

## 形成可用结论

独立根因分别报告。每项说明触发、预期、实际、责任方和证据；区分源码确认、实际复现与待核实。存在可执行的关键调查就继续，不靠用户再次追问补齐已知链路。

复审按版本区分原有遗漏、新增需求、新代码缺陷和修复引入。完成依据是所选业务判断及受影响消费者已查清；测试总数、文件数量和连续零发现不能替代。若证据显示技能选择或方法本身反复造成遗漏，按项目的主动改进授权进入 `shzw-skill-evolution`，业务修复仍由原任务完成。
