# 代码与工程审查

从当前项目的真实业务入口判断缺陷，给出可达触发、判断依据、影响与责任位置。项目源码和命令由目标项目入口定位；技能安装位置不代表被审查项目。

用户明确要求全面或逐项评估门槛、限制与资源预算时，按[门槛与资源预算评估](modes/engineering/references/threshold-budget-assessment.md)直接展开，结合机制取舍及实际负载判断。用户主动讨论当前项目资源预算或操作限制是否合理，或担心持续遇到多类限制，但本轮只要求局部分析时，先完成原问题，再明确用一句话提醒可以对当前项目做一次全面门槛与资源预算评估。提醒不扩大本轮范围；单点故障、单纯查询参数、无关话题或用户明确不要建议时不机械追加。

前端页面 review、视觉检查、审美评价或截图评审，先进入[前端视觉与体验评审](modes/frontend/GUIDE.md)。逐页检查真实画面，再按需补查响应式和交互；“没有错位”不足以证明视觉完成度。纯截图评审以图中位置和可见影响为依据，不要求先取得源码。前端逻辑或接口 diff 沿下方代码审查方法；存在受影响画面时补查该画面，不自动扩成全站审美评审。

## 恢复范围与授权

只读 review 保持只读；“请修复”接续已确认问题实施，“再 review”复查原范围。已有实施授权中的自查结束后继续原任务，不停在建议。新要求只改变命中部分，已接受的业务目标与约束继续有效。

用户对当前审查、缺陷或修复结果说“请校准”“矫正”“纠偏”等时，结合上下文复核对应判断及原范围，不只润色报告，也不自动转成技能维护或产品修复。用户明确更正已沉淀判例，或较晚确认的纠正与同一对象、同一范围的判例冲突时，按现有授权经技能进化入口更新唯一来源及已授权副本；不把一时任务条件或尚未确认的提问升级为长期规则。只有对象无法从上下文确定时才询问。纯方案判断仍由方案入口负责。

代码、工程或业务链审查要主动查阅[业务判断校准判例](modes/engineering/references/judgment-calibration.md)，按索引定位相关方法与专题文档后检索，不能只依赖本次项目聊天或固定案例。按实际动作、身份、数据、资源和失败状态寻找用户尚未指出的遗漏，也反证拟报告问题与修复建议。判例是可更新的调查线索，不是当前产品事实或普遍例外；以本次用户决定和责任项目现行契约、源码及证据判断。未命中的专题不扩张审查。

处理非主干分支的更新、合入或退役时，将创建账号、实际任务归属、分叉基线和双方独有变更作为判断上下文。创建者与用户的 GitHub 账号对照；提交作者、PR 作者和分支名不能单独证明创建者。其他人创建的分支不擅自处理；归属不明时保留分支，说明证据并继续不受影响的工作。只读审查及共享主干的日常维护照常进行。

## 1. 固定对象并列出本次检查项

记录当前提交或候选、范围内工作副本差异及实际运行来源。指定 diff 时，用 Git 的文件清单核对新增、修改、删除与未提交文件，再追直接消费者；项目审查从当前路由、公开导出、注册与构建入口枚举业务链，不能缩成最近 diff。用户要求逐文件或逐页时，保留完整文件或画面清单，分组后核对没有遗漏。文件存在不证明入口可达，文件分组完整也不证明业务检查完整。

先枚举文件名与长度，再沿入口、编译声明和实际引用确定本次内容检索的文件集合，记入下面的检查记录。目录混有已确认无关的原件时，向检索工具传入源码文件集合或相关子树，不能为合并调用改查公共父目录。资源目录或无扩展名文件若作为源码使用，仍须纳入；文件职责不明时先查消费者，不能按目录名或后缀排除。业务确需解析或校验的二进制资源按其接口读取，保留原件且不参与本次判断的归档不读正文。

从现行产品规则建立判断：谁对什么对象做什么，何时允许或拒绝，由谁保存结果，下一环节如何读取。规则约束单次调用、整个定义还是某个使用场景，须先查清；一次调用成功不能证明整个定义具备资格。契约冲突只暂停依赖它的判断，继续其他明确范围。

对照需求的项目审查沿用原需求编号或条款，分别记录实现支持与验证状态；再从实际路由、工具、配置和已交付消费者反查遗漏的能力。区分违反目标、尚未实现与现状文档过时，不能用当前实现覆盖已确认目标。评估替代方案时，按原入口、业务动作、数据结果、权限、联动和失败恢复逐项对应；已有能力须有承接证据才能退役。陌生调用链先说明每一步依赖谁保证前提、由谁保存结果，再判断缺陷；函数名和注释不能代替被调用实现。

多入口、跨文件或项目审查在当前工作记录中保留下表；局部小改可以用一条记录表达相同事实。记录用于驱动调查，不创建永久台账，不要求用户补写。

| 入口、责任位置与源码集合 | 具体规则及依据 | 生产者与消费者 | 正常及相关失败场景 | 结果与证据 |
|---|---|---|---|---|
| 当前路由、操作或构建入口；已核实的源码文件或子树 | 可观察的允许、拒绝或结果约束 | 写入、读取、异步处理及后续操作 | 实际可达的状态或输入组合 | 待查、未发现问题、确认问题、不适用或证据缺口；附位置或实测结果 |

先用下面的维度筛选适用项，再把它们落实到具体入口和场景。一个检查项可覆盖多个维度，无需展开所有笛卡尔组合。不能只记“权限已查”；未执行、超时或上下文不足不能记为不适用。

| 维度 | 本次需查什么；何时补读专项 |
|---|---|
| 业务与职责 | 具体业务结果、现有平台能力、真实所有者及重复机制。只有本次审查对象包含 XRain 平台构建器、安装器、执行器等内部实现时，才读 [XRain 方法](modes/xrain/GUIDE.md)；仅消费公开能力的业务应用包沿本主方法和下方包资源合同审查，不因资源 kind 或 API 名称进入平台内部模式。Workforce 业务读 [Workforce 方法](modes/workforce/GUIDE.md) |
| 身份与授权 | 认证主体、租户成员、执行身份、对象与字段权限；入口到实际生效时是否仍获权，并保留合法相邻场景 |
| 数据与状态 | 默认值、映射、保存与回读、事务和并发、唯一性、迁移及共享定义；只选本次存在的状态与持久化点 |
| 异步与失败 | 切换、取消、撤权、异常、迟到、重试及恢复；区分本地结束、远端未受理和远端结果未知 |
| 资源与性能 | 实际持有者、释放、失效、查询或队列增长与负载放大；涉及资源机制时读 [工程方法](modes/engineering/GUIDE.md)。语言特性、AI 代码隐患及规模/并发/长时审查再读 [语言与运行时](modes/engineering/references/language-runtime.md)，按实际版本筛选，性能结论须有对应负载和预算依据 |
| 消费与兼容 | 公开接口、配置、文件、快照、包与锁文件是否在真实消费者中保持同一含义；涉及构建、启动、文件消费或退役时读工程方法。客户端消费设置、限制或执行结果时，按[规则所有者与客户端消费](modes/engineering/GUIDE.md#规则所有者与客户端消费)核对生效范围、当前能力和原始结果 |
| 测试与证据 | 断言是否保护业务结果，替身是否删掉原故障条件；受影响的合法路径和失败路径是否真正执行，不用测试数量证明覆盖 |
| 界面与交互 | 当前画面、反馈与可达操作是否支持用户任务；页面或截图 review 进入 [前端方法](modes/frontend/GUIDE.md)，逻辑 diff 只补受影响画面 |

同类遗漏、修复反复或多轮结论合并命中时，读取 [反复缺陷方法](modes/engineering/references/recurring-defects.md)。专项由实际对象和风险触发，不等用户再次点名。无需加载未命中的资料，也不强制子智能体；当前执行者可顺序完成以下步骤。

## 2. 分别检查适用项

按已列入口逐项追踪调用、条件和后置结果；新发现的同一规则消费者及时补入记录。先保存候选的触发、依据、影响和未确认条件，再继续其余适用项。找到一个严重问题不能代替其他范围的检查；只读审查不转去修复产品。存在及时通知的必要时先报该发现，原范围继续调查。

类型、测试和搜索用于证明具体判断。需要动态证据时选择能区别正确与错误行为的最小复现；充分静态证据可以成立，不强制每项运行服务。工具失败或输出截断时保留已查与待查对象，按缺口继续，不能静默丢弃其余范围。

缩小正则匹配结果不保证少读文件，先核对工具的扫描范围。定位结果提供字节位置时，直接读取该位置附近的原文窗口；行号不能当作字节偏移。大段原文按缺口分批读取；没有范围接口时，可一次捕获结果后分批展示。控制每批实际展示的总量，避免截断后反复全文搜索同一批内容；新的业务定位与必要完整扫描仍按检查目标执行。

### 核对平台复用与实际运行

XRain 业务先查对象自带字段、Owner、分享、历史、有效授权和已配置的函数/编排；新增同类表或处理器时，核对是否确有独立业务事实。不能只审新代码内部正确，却漏掉重复造平台能力或绕过现有授权的设计。相关语义按需读[对象基础](https://github.com/xingshukeji/skills-hub/blob/main/skills/shzw-workforce-business-development/references/object-foundation.md)与[授权](https://github.com/xingshukeji/skills-hub/blob/main/skills/shzw-workforce-business-development/references/authorization.md)。

调查业务闭环、线上缺失资源或提出修复交付建议时，按需读取[业务逻辑承载](https://github.com/xingshukeji/skills-hub/blob/main/skills/shzw-workforce-business-development/references/implementation.md#选择承载业务逻辑的地方)和[项目源码与制品边界](https://github.com/xingshukeji/skills-hub/blob/main/skills/shzw-workforce-business-development/references/project-structure.md)。对照实际项目描述、源码和交付合同区分包资源、独立租户函数及租户配置；线上缺失不证明源码缺失或应现场新建。只读审查保持只读。

审查 XRain 包受管资源的源码或交付完整性时，按[包编写合同](https://github.com/xingshukeji/skills-hub/blob/main/skills/shzw-xrain-app-package/modes/authoring/references/authoring.md)和[kind 字段合同](https://github.com/xingshukeji/skills-hub/blob/main/skills/shzw-xrain-app-package/modes/authoring/references/kinds.json)逐项比较实际声明。每种命中的 kind 都核对身份前缀、必填字段及包内引用闭包，记录“声明值 → 合同要求 → 符合、差异或待核依据”；再检查宿主与快照是否引用同一合法资源。字符串相同不能代替格式合法，版本记录也不能代替父定义及其当前版本引用。已有离线校验入口可用时运行并审查诊断；不能运行时完成上述静态对照，不把读过合同记成校验通过。发现已交付身份与合同不符时先报告具体差异并核对原制品、目标协议版本，不自行重建身份；纯租户配置、独立函数开通和无包资源的任务不因此加载包编写资料。

Workforce 公共改动追到实际应用、页面和工具，身份链区分认证主体、租户成员及执行绑定。核对消费者安装的包和锁文件，源码已改不证明当前应用加载了它；元数据、HTTP 返回、SDK 转换和页面保存须接得上。内部审查可追责任源码，业务消费者只靠公开能力也应能完成。界面中的状态和解释须服务用户业务判断，不能把内部职责说明当作产品功能。

## 3. 反证候选并搜索同类入口

复用检查记录中的源码集合反查实际消费者；新增路径由引用、路由或编译声明补入，不能在反查时丢掉已确定的文件边界。公共身份、会话、缓存或保存机制的问题，同一对象的查看、编辑、重试和后续处理可能走不同入口。对异步结果核对发起与完成时的主体、对象、版本及页面或执行生命周期，选择真实可达的切换、取消、失败和重试分支。

确认一个根因后，先用搜索命中原实例，再从函数、字段、状态写入和业务动作扩展到别名、包装器及不同实现。记录搜索边界，逐个核验候选的真实调用与保护；不能只搜索出错函数名。停止条件是本次范围内受同一规则约束的入口都有处置，而不是搜索没有新字符串。没有同类路径时以入口和消费证据说明，不扩大为整仓猜测。

本次新增或改写的共享状态、协议及快照，也要从产生者追到每个实际消费者；按存在的路径核对计划冻结、回读、执行、异步处理和清理是否理解同一合同。生产者或替身测试通过不能代替消费者的行为证据；没有这些路径的小改不扩展整仓审查。

例如，保存按钮禁用只保护该按钮。若侧栏仍允许离开，必须继续追保存回调能否修改新页面的导航和草稿。这个例子证明要检查实际可达的旁路，不要求所有业务机械套用同一检查表。

每个候选问题都找反证：入口是否退役、调用方是否已保护、后置状态是否在承诺时点纠正、正常相邻场景是否依赖现行为。反证只排除它覆盖的条件；依赖特定输入、撤权、并发或恢复状态不构成排除理由，须核实这些条件是否可达。已退役内容改查构建、路由和交付残留，不将其界面问题当作当前用户缺陷。

分别保留直接观察、推导后果与待验证影响。严重性由可达影响决定；本地取消不能证明远端撤回，资源滞留也不能单独证明需要容量上限。用相邻合法场景校准建议，避免取消正确隔离、全量拒绝或改写合法配置来消除局部现象。

对会提交、发布或批量写入的多步操作，顺着“检查状态 → 等待、钩子或并行修改 → 实际生效 → 结果回读”核对关键条件是否仍成立。例如提交前暂存范围正确，不代表钩子后的提交仍然正确；比较最终提交与预期，并区分本地已提交和远端已生效。仅对实际存在状态变化或外部副作用的路径展开。

## 4. 对照检查项后报告

回看最初范围、适用维度和调查中新增的入口，逐项消除“待查”：未发现问题须有已核实的规则和证据；不适用须有对象或边界依据；证据缺口须有具体缺失条件及其影响。不能用发现清单反推覆盖清单，也不能把“已读文件”“测试通过”当作所有维度已查。大型范围分批保留证据，最终汇总全部批次。

存在可执行的关键调查就继续；已知缺口不能靠加提示、写限制或建议后续处理来宣告通过。确有外部阻断时报告已检查范围、未检查的入口或状态和最小恢复条件，不把该部分归为无问题。只读审查可以完成并交付已证实缺陷；修复任务须验证修复的后置结果。不要混淆“发现问题”“检查完成”和“问题已修复”。

独立根因分别报告。每项说明触发、预期、实际、责任方和证据；区分源码确认、实际复现与待核实。只有同一责任处置能消除各个反例时才合并，并保留全部受影响入口。建议、未验证风险与确证缺陷分别表达，不凑发现数量。

复审按版本区分原有遗漏、新增需求、新代码缺陷和修复引入；未重查的旧问题不能因本轮未报告就判已解决。已有修复授权时，原反例、同类入口及相邻合法场景验证通过后继续原任务。测试总数、文件数量、固定轮数和连续零发现均不替代这些证据，也不承诺零缺陷。

若证据显示技能选择或方法本身造成遗漏，按项目的主动改进授权进入 `shzw-skill-evolution`。维护时使用 [隔离执行案例](https://github.com/xingshukeji/skills-hub/tree/main/evals/skill-execution)；原始请求与评判答案分开。作者走查、结构校验和独立执行分别报告，不能用文档通过证明漏检已降低。方法取舍见 [开源来源](modes/engineering/references/open-source.md)。
